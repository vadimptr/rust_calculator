## Кратко

Устройство «мерцает» (`IOEntity.IsFlickering`), если его состояние менялось **больше 5 раз
подряд с промежутками не больше 1 с**, и с последнего изменения прошло меньше 1 с. Это защита
от «пилы»: на быстро меняющемся сигнале потребители и батареи ведут себя так, будто питание
есть всегда.

У защиты есть побочный эффект. Батарея в режиме мерцания заряжается по **максимуму** из
последних пяти значений входа и без своего ограничения `4 × maxOutput`. Отсюда известные
трюки с «мультиплексированием» заряда.

## Как работает

### Определение

```
IOStateChanged():                     // при каждом изменении входа/выхода
    если прошло > 1 с с прошлого изменения: changedCount = 1
    иначе: changedCount += 1
    lastChangeTime = сейчас

IsFlickering() = changedCount > 5 и (сейчас − lastChangeTime) < 1 с
```

- Считается любое изменение: новое значение на входе (`UpdateFromInput`, если изменились
  `currentEnergy` или выход) и изменение выхода через `MarkDirty`/`TouchInternal`.
- Первые 5 изменений «бесплатны». Шестое подряд включает режим.
- Режим держится, пока изменения идут чаще раза в секунду. Через 1 с тишины он гаснет сам.
- Счётчик у каждого устройства свой. Мерцает не вся сеть, а те устройства, на которых меняется
  сигнал.

### Кто ведёт себя иначе при мерцании

Полный список по коду (поиск `IsFlickering`):

| Класс | Что меняется | Где |
|---|---|---|
| Любое устройство (`IOEntity`) | `DesiredPower` возвращает полное потребление, даже если питания не хватает. Батарея считает такое устройство нагрузкой всегда | `IOEntity.DesiredPower` |
| Батарея | Заряд и `DesiredPower` по максимуму из истории последних 5 входов, **без** ограничения `maxOutput × maximumInboundEnergyRatio`. Подзарядка не отменяется при пропадании входа | `ElectricBattery.IOStateChanged`, `DesiredPower`, `AddCharge` |
| Блокировщик | Вход питания «хочет энергии» даже когда блок включён (`WantsPower(0)` = true) | `ElectricalBlocker.WantsPower` |
| OR | Оба входа «хотят энергии», а не только сильнейший | `ORSwitch.WantsPower` |
| Ячейка памяти | `AllowDrainFrom` = true для обоих выходов: батарея видит нагрузку на обоих | `ElectricalDFlipFlop.AllowDrainFrom` |
| Прожектор (`SearchLight`) | При каждом включении питания в режиме мерцания получает **25 урона** | `SearchLight.OnFlagsChanged` |

Прожектор (`searchlight.deployed`, 150 HP) на мигающем питании разрушится за 6 включений.

### Батарея: история входов

```
IOStateChanged(вход):
    если мерцает: inputHistory ← вход   (хранит последние 5 значений, включая нули)

DesiredPower():
    если полная: 0
    если не мерцает: min(вход, floor(maxOutput × 4))
    если мерцает:    max(inputHistory)              ← без ограничения 4×

AddCharge()  (раз в ~1 с):
    заряд += min(мерцает ? max(inputHistory) : вход, DesiredPower()) × chargeRatio
```

Следствия, проверенные по коду:

1. **Мигающий вход заряжает как постоянный.** Если вход скачет 20 → 0 → 20 → 0, в истории
   всегда есть 20, и раз в секунду в батарею идёт `20 × 0.8 = 16` rWs. Хотя средняя мощность
   входа — 10.
2. **Снимается лимит 4×.** Малая батарея (`maxOutput` 15) обычно берёт не больше 60 rW.
   В режиме мерцания она возьмёт весь пик: ветряк на 150 rW даст `150 × 0.8 = 120` rWs/с
   вместо 48.
3. **История не очищается.** После выхода из режима старые значения остаются в очереди
   и снова участвуют, когда мерцание начнётся опять (пока их не вытеснят 5 новых).
4. Заряд не прерывается: при мерцании `IOStateChanged` не отменяет `AddCharge`, даже если
   в данный момент вход 0.

## Генератор колебаний (осциллятор)

### Схема

```
 источник ──► [Блокировщик] ──► [Сплиттер] ──► выход 1 ─┐
              вход 0 (питание)             └─► выход 2 ──► к потребителю / Toggle
              вход 1 (Block) ◄────────────────────────────┘
```

Как это работает по коду:

1. Блок = 0 → блокировщик отдаёт питание → сплиттер → вход Block > 0.
2. `ElectricalBlocker.UpdateFromInput(слот 1)` → `UpdateBlocked` → флаг `On` → `MarkDirty`.
3. Выход блокировщика падает в 0 — но не раньше, чем через `responsetime` (0.1 с) после
   прошлого `UpdateOutputs` ([[io-engine]]).
4. Сплиттер передаёт 0 → блок снят → цикл повторяется.

Проверено:

- У блокировщика **нет проверки петель**. Вход Block в префабе
  `electrical.blocker.deployed` — не `mainPowerSlot`, а `IsConnectedTo` и `SendChangedToRoot`
  ходят только по основным входам. Петля для них невидима ([[circuit-loops]]).
- Серверная проверка провода (`WireTool.RPC_MakeConnection`) не запрещает соединять выход
  с входом того же устройства. Разрешает ли это клиент, по коду сервера не видно. Сплиттер
  между ними решает вопрос и даёт лишний выход для сигнала.

Частота (оценка по коду): полупериод ≈ `responsetime` плюс округление до кадра сервера,
то есть 0.1–0.15 с. Полный период ≈ 0.2–0.3 с, около 3–5 «вспышек» в секунду. Все устройства
после осциллятора видят ≥ 6 изменений в секунду и почти сразу переходят в режим мерцания.
Точная частота зависит от тикрейта сервера и загрузки очереди.

## «Мультиплексирование» заряда

### Идея

[[memory-cell|Ячейка памяти]] (`ElectricalDFlipFlop`) отдаёт **весь** вход питания на один из
двух выходов: на «Output», если включена, иначе на «Inverted Output»
(`ElectricalDFlipFlop.UpdateOutputs`). Если быстро переключать её осциллятором через вход
Toggle, каждая из двух батарей получает полный вход половину времени. Обе мерцают, и каждая
заряжается по пику.

```
 солнечная панель 20 rW
        │
        ▼ Power In
 ┌──────────────┐  Output ─────────► батарея A  (видит 20,0,20,0…)
 │ Ячейка памяти│
 │              │  Inverted Output ► батарея B  (видит 0,20,0,20…)
 └──────────────┘
        ▲ Toggle
        │
 осциллятор (блокировщик + сплиттер, см. выше)
```

Итог по формулам: каждая батарея получает `20 × 0.8 = 16` rWs/с, вместе **32 rWs/с от
источника на 20 rW**. Без трюка одна батарея получила бы 16.

Осциллятору тоже нужно питание, минимум 2 rW: на 1 rW сплиттер отдаёт 1 / 0, и блок или Toggle
остаются без сигнала. Если взять его от той же панели ветвителем (Branch = 2), в ячейку пойдёт 18, и
каждая батарея получит 14,4 rWs/с. 16 rWs/с выходит, если осциллятор питается от выхода батареи A.
Для одной панели выигрыш даёт именно мультиплексирование, а не снятие лимита 4×: 20 rW меньше лимита
любой батареи. Полная схема с расчётами — [[scheme-flicker-two-batteries]].

### Что проверено по коду

| Шаг | Проверено | Где |
|---|---|---|
| Toggle переключает ячейку при переходе 0 → >0 | да | `GetDesiredState`, `UpdateFromInput` (слот 3) |
| Ячейка отдаёт весь вход на один выход, не делит | да | `ElectricalDFlipFlop.UpdateOutputs`, `GetPassthroughAmount` |
| Одна петля через выход не считается замыканием (нужно ≥ 2 выходов) | да | `DetectShortCircuit` |
| Батарея при мерцании пишет вход в историю и заряжается по максимуму | да | `ElectricBattery.IOStateChanged`, `AddCharge` |
| Режим мерцания включится: батарея видит смену каждые ~0.2 с | да, по формуле `IsFlickering` | `IOEntity.IOStateChanged` |
| Реальная частота осциллятора на живом сервере | **нет**, оценка | зависит от тикрейта и очереди |
| Работа в игре | **не проверено**, это вывод из кода | — |

Схему можно расширять: на каждом выходе ячейки — ещё одна ячейка с тем же Toggle. Условие для
каждой батареи одно: её вход должен меняться чаще раза в секунду, а пик — быть среди последних
пяти значений.

### Где трюк не работает

- **Если источник — батарея.** Её расход (`GetDrain`) суммирует `DesiredPower` нагрузки.
  Мерцающие батареи-потребители запрашивают свой пик, а ячейка памяти при мерцании открывает
  оба выхода для подсчёта (`AllowDrainFrom`). Источник платит за оба выхода (не больше своего
  `maxOutput`).
- Выигрыш есть только у источников, которые не следят за нагрузкой: солнечная панель, ветряк,
  топливный генератор, водяное колесо.

Теоретическое следствие: батарея A, которая через мерцающую ячейку питает и себя, и батарею B,
тратит не больше `maxOutput`, а заряжает обеих по `maxOutput × 0.8`. По формулам это даёт
прибыль энергии из ничего. В игре не проверено.

**Важно.** На многих серверах такие схемы (осцилляторы ради заряда, «бесконечные» батареи)
считаются абузом бага и наказываются. Описание приведено, чтобы понимать механику.

## Нюансы

- Мерцание включает и «честные» схемы: мигающая гирлянда через таймеры, быстро моргающий
  датчик. Батарея за такой схемой будет тратить заряд на потребителей даже в моменты,
  когда им не хватает питания (`IOEntity.DesiredPower`).
- Прожектор на мигающем питании сам себя ломает (25 урона за включение).
- Через 1 с без изменений режим снимается, и батарея возвращается к лимиту 4×.
