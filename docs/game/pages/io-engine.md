## Кратко

Электросеть в Rust — это не «расчёт цепи», как в физике. Каждое устройство (`IOEntity`) помнит
своё входное значение и **толкает** результат дальше по проводам. Изменение входа ставит
устройство в очередь. Раз в кадр сервер разбирает очередь в пределах бюджета времени.
Каждое устройство обновляет свои выходы не чаще раза в `ioentity.responsetime` = **0.1 с**.

Отсюда почти все «странности» электрики: сигнал идёт по цепочке с задержкой, короткие импульсы
теряются, в петлях возникают колебания, а батарея узнаёт о нагрузке отдельным обходом.

## Как работает

### Одно устройство: три шага

```
провод от соседа
      │  UpdateFromInput(значение, слот)       ← вызывается соседом немедленно
      ▼
 ┌─────────────────────────────────────────┐
 │ UpdateHasPower → флаг Reserved8 (запитан)│
 │ currentEnergy = CalculateCurrentEnergy() │   обычно = значение на входе
 │ если currentEnergy или выход изменились: │
 │    IOStateChanged() (счётчик мерцания)   │
 │    ensureOutputsUpdated = true           │
 │ встать в очередь своего типа             │
 └─────────────────────────────────────────┘
      │           …позже, когда очередь дойдёт…
      ▼
 UpdateOutputs():
   если с прошлого обновления < responsetime → встать в конец очереди, выйти
   если ensureOutputsUpdated = false → выйти
   для каждого выхода i по порядку 0,1,2…:
       сосед.UpdateFromInput(GetPassthroughAmount(i), его_слот)
```

- `GetCurrentEnergy()` по умолчанию = `clamp(currentEnergy − ConsumptionAmount(), 0, currentEnergy)`.
- `GetPassthroughAmount(i)` по умолчанию = `GetCurrentEnergy() / cachedOutputsUsed`, целочисленно.
  `cachedOutputsUsed` — число выходов, где на том конце живое устройство (`UpdateUsedOutputs`).
- `UpdateFromInput` у соседа вызывается **сразу**, внутри `UpdateOutputs`. А вот его собственные
  выходы обновятся только когда очередь дойдёт до него.

Важно: базовый `CalculateCurrentEnergy` просто возвращает значение **того входа, который
сейчас обновился**. У устройства с несколькими входами без своей логики последний обновлённый
вход затирает остальные. Поэтому все логические элементы (OR, AND, сумматор, блокировщик)
хранят входы в своих полях.

### Очереди и бюджет кадра

`IOEntity.ProcessQueue` вызывается из `ServerMgr` каждый серверный кадр. Очередей шесть
(`QueueType`), каждая — обычная FIFO-очередь:

| Очередь | Кто в неё попадает | Бюджет, мс за кадр (ConVar) |
|---|---|---|
| `ElectricHighPriority` | электрика без `sourceItem` — монументы, пазлы | `ioentity.framebudgetelectrichighpriorityms` = 1 |
| `ElectricLowPriority` | электрика игроков (есть `sourceItem`) | `ioentity.framebudgetelectriclowpriorityms` = 0.5 |
| `Fluidic` | вода | `ioentity.framebudgetfluidms` = 0.25 |
| `Kinetic` | кинетика (монументы) | `ioentity.framebudgetkineticms` = 1 |
| `Generic` | «прочее», помечено как неиспользуемое | `ioentity.framebudgetgenericms` = 1 |
| `Industrial` | конвейеры, адаптеры | `ioentity.framebudgetindustrialms` = 0.25 |

Очередь выбирается по `ioType` устройства (`GetQueueType`): `Electric`, `Fluidic`, `Kinetic`,
`Generic`, `Industrial`. Тип провода (`IOSlot.type`) проверяется отдельно: если тип входа
не совпадает с типом устройства, `UpdateFromInput` только отмечает изменение
(`IOStateChanged`) и ничего не пересчитывает. Так, например, водяной насос получает
электричество на вход, а сам числится жидкостным.

Разбор одной очереди за кадр идёт, пока:

1. очередь не пуста;
2. не истёк бюджет этой очереди;
3. устройство в голове очереди **ещё не было отложено в этом кадре**
   (`HasBlockedUpdatedOutputsThisFrame`).

Третье условие — защита от бесконечного цикла. Устройство, которому рано обновляться
(`ShouldUpdateOutputs` вернул false), уходит в конец очереди и запоминает номер кадра. Когда
оно снова оказывается первым в том же кадре, разбор этой очереди останавливается до следующего
кадра. Итог: за кадр очередь проходится максимум «один круг».

Бюджет общий на весь сервер. 0.5 мс на всю электрику всех игроков — немного. На загруженном
сервере очередь не успевает разобраться за кадр, и сигнал по большой схеме ползёт заметно
медленнее, чем на пустом.

### Троттлинг: responsetime

`ShouldUpdateOutputs`: если с прошлого `UpdateOutputs` прошло меньше `ioentity.responsetime`
(0.1 с), устройство встаёт в конец очереди. Иначе запоминает время, отправляет клиентам
флаги и продолжает.

Следствия:

- **Каждое устройство в цепочке — это до 0.1 с задержки** при частых изменениях. При редких
  изменениях устройство обновляется в том же кадре, если очередь до него дошла.
- **Импульс короче 0.1 с может потеряться.** Выходы считаются в момент `UpdateOutputs`,
  а не в момент изменения входа. Если вход успел стать 5 и вернуться в 0 до того, как
  устройство обновилось, соседи увидят только 0, то есть ничего.
- **Время тратится и на «пустые» записи.** `UpdateFromInput` ставит устройство в очередь
  каждый раз, даже если оно уже там. Лишняя запись после истечения 0.1 с вызовет
  `ShouldUpdateOutputs`, обновит метку времени и ничего не сделает
  (`ensureOutputsUpdated` = false). Следующее реальное изменение будет ждать новые 0.1 с.

Исключение — монументный генератор `ElectricGenerator`. Он переопределяет `UpdateOutputs`
без `ShouldUpdateOutputs` и толкает выходы без троттлинга.

### Порядок обхода

- Выходы обрабатываются **по номеру слота**: 0, 1, 2. Сосед на выходе 0 получает значение
  раньше соседа на выходе 1, и раньше встаёт в очередь.
- Очереди разбираются по порядку словаря `_processQueues` (сначала высокий приоритет,
  затем игроки, вода, кинетика, generic, индустриальная).
- Порядок важен там, где элемент реагирует на **фронт** — изменение значения: переключатель
  «Toggle» у ячейки памяти, вход «Increment» у счётчика, вход таймера, RAND. Если два сигнала
  приходят в один кадр, результат зависит от того, какой провод обработан первым.

### Корневые устройства и изменение схемы

`IsRootEntity()` = true у батареи, сплиттера, сумматора, солнечной панели, ветряка, водяного
колеса, топливного и монументного генераторов, нажимной плиты, мишени, микрофонной стойки,
точки доступа к энергосети и жидкостных контейнеров.

- **После загрузки сервера** `IOEntity.Init` у каждого корневого устройства через 1 с вызывает
  `MarkDirtyForceUpdateOutputs`. Поле `currentEnergy` в сохранение не пишется. Схема «оживает»
  заново от корней: источники снова толкают значения вниз. Состояния, которые хранятся во
  флагах (включён ли выключатель, состояние ячейки памяти), переживают рестарт.
- **Подключение провода** (`ConnectTo`) и **отключение** (`Disconnect`) вызывают
  `SendChangedToRoot(forceUpdate: true)`. Метод поднимается вверх по **основным** входам
  (`mainPowerSlot`) до корней и вызывает у них `OnCircuitChanged`. Батарея в ответ сразу
  пересчитывает расход (`GetDrain`), сплиттер — выходы. Повторные посещения отсекаются списком
  `existing`, поэтому петли здесь не страшны.
- `MarkDirty()` пересчитывает число подключённых выходов и вызывает `TouchIOState` →
  `TouchInternal`. Если выход изменился, это считается изменением состояния (для [[flicker]]),
  и устройство встаёт в очередь.

### Основные и вспомогательные входы

У каждого входа в префабе есть флаг `mainPowerSlot`. Основной вход — это «питание». Вход
блокировки у блокировщика, Set/Reset/Toggle у ячейки памяти, Increment у счётчика, «Switch On»
у выключателя — не основные. От этого зависит:

- `DesiredPower` по умолчанию возвращает 0 для неосновного входа — батарея не тратит заряд
  на сигнальные провода;
- поиск петель (`IsConnectedTo`) и `SendChangedToRoot` идут только по основным входам.
  Сигнальная обратная связь для них невидима. Подробнее — [[circuit-loops]].

### Режим бесконечной энергии

`ioentity.infiniteiopower` (по умолчанию false). При включении каждый игровой электрический
и индустриальный `IOEntity` получает 999 на все основные входы (`ApplyInfinitePower`),
а `TouchInternal`/`UpdateFromInput` подменяют выход на 999. При выключении устройства без
подключённых входов получают 0. Высокоприоритетная (монументная) электрика не затрагивается.

### Как батарея узнаёт о нагрузке

Push-модель передаёт только «сколько подано». Сколько реально потребляется, сеть не считает.
Батарея делает это отдельно: раз в ~1 с (`ElectricBattery.CheckDischarge`) она обходит дерево
вниз (`AddConnectedRecursive`) и суммирует `DesiredPower` потребителей. Подробнее —
[[battery]] и [[electricity-quirks]].

## Нюансы

- **Сигнал не мгновенный.** Цепочка из N устройств при частых переключениях отвечает
  с задержкой до N × 0.1 с. Длинные цепочки логики «тормозят» и могут разъезжаться по времени.
- **Короткие импульсы теряются.** Кнопка и нажимная плита дают импульс 0.5 с, это безопасно.
  Сигнал, который меняется быстрее 0.1 с, вниз по цепочке может не пройти.
- **Значения в моменте не «текут обратно».** Если потребитель ниже по цепочке недополучил
  питание, это никак не влияет на устройство выше: оно уже отдало своё значение.
- **После рестарта** схема пересобирается от корней через ~1 с после загрузки. Устройства,
  которые хранят состояние только в памяти (входы логики), получают его заново от соседей.
  Таймер, который тикал в момент рестарта, начинает отсчёт заново (`TimerSwitch.PostServerLoad`,
  см. [[timer]]).
- **Типы проводов не смешиваются.** Электрический провод нельзя подключить к входу воды
  (`WireTool`: `inputs[i].type != wireType`).

## На практике

- Не стройте длинных последовательных цепочек логики там, где важна скорость (ловушки,
  турели). Каждое звено — потенциальные 0.1 с.
- Для «одновременного» срабатывания разводите сигнал сплиттером, а не цепочкой.
- Если схема «не просыпается» после рестарта, проверьте, что у неё есть корневой источник.
  Батарея, панель, генератор и сплиттер сами перезапускают схему.
