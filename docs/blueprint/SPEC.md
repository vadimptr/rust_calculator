# Rust Base Blueprint — спецификация формата v1.0

Формат JSON-документа, описывающего постройку в Rust: строительные блоки,
их соединения, шкаф (Tool Cupboard) и двери. Документ предназначен для
приложения-конструктора в этом репозитории: по нему считается геометрия,
проверяется корректность постройки, рисуется 3D и считаются стоимость
постройки, апкипа и рейда.

Состав:

| Файл | Назначение |
|---|---|
| `docs/blueprint/SPEC.md` | этот документ |
| `docs/blueprint/schema/blueprint.schema.json` | формальная JSON Schema (draft 2020-12) |
| `docs/blueprint/examples/*.json` | проверенные схемой примеры |

Данные игры в документе сверены с обновлением **2026-09** (Breach and Clear).
Числа игры меняются ежемесячно, поэтому каждый чертёж хранит `meta.gameVersion`.

---

## 1. Принципы

1. **Граф, а не координаты.** В авторском слое нет ни одной координаты.
   Ровно один фундамент — **корень** (`root`), это ячейка, на которой стоит
   шкаф. Все остальные блоки описывают *к чему* и *чем* они крепятся
   (`attach`). Это повторяет механику игры: блоки ставятся в сокеты
   соседних блоков, а не в произвольную точку. Мировые координаты
   появляются только в вычисляемом слое, где корень стоит в начале
   координат.
2. **Два слоя.** Авторский слой (`elements`, `deployables`) — источник
   истины, его пишут люди и ИИ. Вычисляемый слой (`resolved`) — результат
   работы движка геометрии, он никогда не редактируется руками и
   пересчитывается при любом изменении авторского слоя.
3. **Один каталог.** Идентификаторы типов блоков (`kind`) совпадают с `id`
   из `src/data/blocks.ts`, поэтому расчёт стоимости и апкипа работает
   напрямую по чертежу без таблиц соответствия.
4. **Детерминизм.** Один и тот же авторский слой всегда даёт один и тот же
   `resolved` с точностью до округления до 1 мм.
5. **YAGNI.** В v1.0 входят только блоки строительного плана, шкаф и
   двери. Всё остальное (печи, ящики, турели, электрика, внешние стены)
   добавляется в следующих версиях без изменения существующих полей.

## 2. Термины

| Термин | Значение |
|---|---|
| Элемент (element) | Строительный блок из строительного плана: фундамент, стена, пол, лестница, крыша. Имеет `grade`. |
| Объект (deployable) | Размещаемый предмет: шкаф, дверь. Не имеет `grade`, материал зашит в `kind`. |
| Ячейка (cell) | Площадь, занимаемая фундаментом или полом: квадрат 3×3 м или равносторонний треугольник со стороной 3 м. |
| Сокет (socket) | Именованная точка крепления на элементе. Каждое соединение — пара «сокет родителя — сокет ребёнка». |
| Уровень (level) | Этаж. `0` — плоскость фундаментов, `1` — на высоте полной стены (3 м). Половинные стены дают уровни с шагом `0.5`. |
| Grade | Материал блока: `twig`, `wood`, `stone`, `metal`, `armored`. |

## 3. Структура документа

```jsonc
{
  "$schema": "../schema/blueprint.schema.json",   // необязательно
  "formatVersion": "1.0",                          // обязательно, фиксировано
  "meta": { ... },                                 // обязательно
  "defaults": { "grade": "stone" },                // необязательно
  "elements": [ ... ],                             // обязательно, ≥ 1, ровно один root
  "deployables": [ ... ],                          // необязательно
  "resolved": { ... }                              // необязательно, генерируется
}
```

### 3.1 `meta`

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `name` | string ≤ 120 | да | Название чертежа |
| `description` | string | нет | Произвольное описание |
| `author` | string | нет | Автор |
| `createdAt` | date-time | нет | ISO 8601 |
| `gameVersion` | string | нет | Месяц обновления игры, например `"2026-09"` |
| `tags` | string[] | нет | Уникальные теги |

### 3.2 `defaults`

`defaults.grade` — материал для элементов без собственного `grade`.
Если ни `defaults.grade`, ни `element.grade` не заданы, движок
использует `twig` (как в игре при установке блока).

### 3.3 Идентификаторы

`id` — строка по шаблону `^[a-z][a-z0-9_-]{0,63}$`, уникальна в пределах
документа среди элементов **и** объектов вместе.

## 4. Геометрический справочник

### 4.1 Система координат

- Единицы — метры, углы — градусы.
- Ось **Y** направлена вверх. Плоскость **(x, z)** — горизонтальная «планировка».
- Угол `θ` в плоскости отсчитывается от оси `+x` к оси `+z`:
  направление с углом `θ` равно `(cos θ, sin θ)` в координатах `(x, z)`.
- `rotation` элемента — угол его локальной оси `+x` в мировой плоскости.
  Все повороты в документе кратны 30°, поэтому движок сравнивает углы по
  модулю 360 с допуском 0.01°.
- Для Three.js (правая система, Y вверх) мировой угол вокруг оси Y равен
  `−θ`. Это единственное место, где знак меняется; формат сам по себе
  от рендера не зависит.

Начало координат — центр корневого фундамента, его `rotation = 0`, а
верхняя плоскость лежит на `y = 0`. Уровень `level = y / 3`. Все
фундаменты одного дерева лежат на одной высоте, как и в игре: перепады
рельефа формат не описывает (см. §13).

### 4.2 Размеры блоков

Константы движка геометрии. Значения, помеченные `≈`, взяты из
наблюдений, а не из файлов игры; они вынесены в одну таблицу констант,
чтобы их можно было уточнить без изменения формата.

| Константа | Значение | Комментарий |
|---|---|---|
| `GRID` | 3.000 м | сторона квадратной ячейки и любого ребра |
| `SQ_APOTHEM` | 1.500 м | от центра квадрата до середины ребра |
| `SQ_CIRCUM` | 2.121 м | от центра квадрата до вершины |
| `TRI_APOTHEM` | 0.866 м | от центра треугольника до середины ребра (`3 / (2√3)`) |
| `TRI_CIRCUM` | 1.732 м | от центра треугольника до вершины (`3 / √3`) |
| `TRI_HEIGHT` | 2.598 м | высота треугольной ячейки |
| `WALL_H` | 3.000 м | стена, проём, оконная рама, рама стены |
| `HALF_WALL_H` | 1.500 м | половинная стена |
| `LOW_WALL_H` | ≈ 1.000 м | низкая стена |
| `ROOF_RISE` | ≈ 3.000 м | подъём крыши от низкого ребра до высокого |
| `FLOOR_T` | ≈ 0.200 м | толщина пола (только для рендера, на сокеты не влияет) |
| `DOORWAY_W × DOORWAY_H` | ≈ 1.3 × 2.2 м | проём `doorway`, одиночная дверь заполняет его целиком |
| `FRAME_W × FRAME_H` | ≈ 2.7 × 2.85 м | проём `wall-frame`: тонкая рамка, гаражная дверь заполняет его целиком |
| `DOUBLE_LEAF_H` | ≈ 2.3 м | высота створок двойной двери; выше — неподвижная часть до верха проёма |
| `WINDOW_W × WINDOW_H`, `WINDOW_SILL` | ≈ 2.2 × 1.3 м, подоконник 0.95 м | проём `window-frame` почти во всю ширину стены; точных чисел в открытых источниках нет, взяты пропорции модели |
| `TC_W × TC_D × TC_H` | ≈ 1.1 × 0.6 × 1.9 м | габарит шкафа: ширина вдоль стены, глубина, высота |

### 4.3 Локальная геометрия ячеек

В локальной системе ячейки центр — в начале координат, `rotation = 0`.
Ребро `edge:k` задаётся углом внешней нормали `θₖ`:

| Форма | `θₖ` | Апофема `a` | Вершины |
|---|---|---|---|
| квадрат | `90° · k`, k = 0..3 | 1.500 | на углах `45° + 90°·k`, радиус 2.121 |
| треугольник | `120° · k`, k = 0..2 | 0.866 | на углах `60° + 120°·k`, радиус 1.732 |

Центр ребра `k`: `a · (cos θₖ, sin θₖ)`. Ребро `edge:0` у обеих форм
смотрит в локальный `+x`.

### 4.4 Сокеты по типам элементов

| `kind` | Форма | Сокеты | Роль сокетов |
|---|---|---|---|
| `square-foundation` | квадрат | `edge:0..3`, `top` | рёбра принимают соседние ячейки и стены; `top` — лестницы и объекты |
| `triangle-foundation` | треугольник | `edge:0..2`, `top` | то же |
| `square-floor` | квадрат | `edge:0..3`, `top` | пол крепится **ребром** к `top` стены или к ребру соседней ячейки; `top` — лестницы и объекты |
| `triangle-floor` | треугольник | `edge:0..2`, `top` | то же |
| `floor-frame` | квадрат | `edge:0..3`, `top` | как пол; `top` не принимает объекты |
| `triangle-floor-frame` | треугольник | `edge:0..2`, `top` | то же |
| `wall`, `half-wall` | ребро | `bottom`, `top`, `face` | `bottom` ставится на ребро ячейки или на `top` другой стены; `top` принимает рёбра полов и крыш и `bottom` стен; `face` — грань стены, принимает дроп-боксы |
| `low-wall` | ребро | `bottom`, `top` | как стена, без `face` |
| `doorway` | ребро | `bottom`, `top`, `opening` | как стена; `opening` принимает одинарную дверь |
| `window-frame` | ребро | `bottom`, `top`, `opening` | как стена; `opening` принимает вставку в окно: стекло или решётку |
| `wall-frame` | ребро | `bottom`, `top`, `opening` | как стена; `opening` принимает гаражную и двойные двери |
| `stairs-l-shape`, `u-shaped-stairs` | ячейка | `bottom` | ставится на `top` квадратной ячейки |
| `roof` | квадрат | `edge:0` (низкое), `edge:1`, `edge:3` (боковые), `edge:2` (высокое) | `edge:0` ставится на `top` стены или на ребро ячейки; боковые принимают соседние крыши |
| `roof-triangle` | треугольник | `edge:0` (низкое), `edge:1`, `edge:2` | как `roof`, вершина напротив `edge:0` поднята |

Сокеты объектов: шкаф занимает `top` ячейки, двери и вставки занимают
`opening`, дроп-боксы вешаются на `face` стены (на одной стене их может
быть несколько, по разным смещениям).

### 4.5 Матрица совместимости

Строка — сокет родителя (`attach.socket`), столбец — тип и сокет ребёнка
(`attach.selfSocket`). Пусто — соединение запрещено.

| Родитель → Ребёнок | фундамент `edge` | пол / рама пола `edge` | стена-тип `bottom` | лестница `bottom` | крыша `edge:0` | крыша `edge:1/3` | шкаф | дверь |
|---|---|---|---|---|---|---|---|---|
| фундамент `edge` | ✔ | | ✔ | | ✔ | | | |
| фундамент `top` | | | | ✔ | | | ✔ | |
| пол / рама `edge` | | ✔ | ✔ | | ✔ | | | |
| пол `top` | | | | ✔ | | | ✔ | |
| рама пола `top` | | | | ✔ | | | | |
| стена-тип `top` | | ✔ | ✔ | | ✔ | | | |
| крыша `edge:1/3` | | | | | | ✔ | | |
| `doorway.opening` | | | | | | | | одинарная |
| `wall-frame.opening` | | | | | | | | гаражная, двойная |
| `window-frame.opening` | | | | | | | | стекло, решётка |

«Стена-тип» — `wall`, `half-wall`, `low-wall`, `doorway`, `window-frame`,
`wall-frame`. Одинарные двери: `wooden-door`, `sheet-metal-door`,
`armored-door`. Двойные: `wooden-double-door`, `sheet-metal-double-door`,
`armored-double-door`.

`selfSocket` можно опустить, если у ребёнка ровно один подходящий сокет
(стены, лестницы, объекты). Для ячеек и крыш `selfSocket` обязателен.

Корневой фундамент ни к чему не крепится, но его рёбра и `top` — такие же
сокеты, как у любой другой ячейки.

### 4.6 Ёмкость сокетов

| Сокет | Слоты |
|---|---|
| `edge` ячейки | один **сосед** (ячейка), одна **крыша** низким ребром (лежит над позицией соседа) и одна **стена-тип** одновременно |
| `top` ячейки | одна лестница **или** любое число объектов, не пересекающихся в плане |
| `top` стены-типа | один пол/крыша **с каждой стороны** (всего до двух) и одна стена сверху |
| `opening` | одна дверь |
| `edge:1/3` крыши | одна крыша |

Два элемента, попавшие в один слот, — ошибка валидации `V05`.

### 4.7 Формулы размещения

Обозначения: `P` — родитель, `C` — ребёнок, `pos` — центр в плане `(x, z)`,
`y` — высота, `rot` — поворот, `n(θ) = (cos θ, sin θ)`, `θₖ` — локальная
нормаль ребра `k`, `a` — апофема.

**Ячейка ребром к ребру ячейки** (`edge → edge`):

```
rot_C = rot_P + θ_k(P) + 180° − θ_m(C)
pos_C = pos_P + (a_P + a_C) · n(rot_P + θ_k(P))
y_C   = y_P,  level_C = level_P
```

**Стена-тип на ребро ячейки** (`edge → bottom`):

```
rot_W = rot_P + θ_k(P)            // нормаль стены смотрит наружу от P
pos_W = pos_P + a_P · n(rot_W)
y_W   = y_P,  level_W = level_P
```

**Стена-тип на верх стены-типа** (`top → bottom`, стопка):

```
rot_C = rot_P,  pos_C = pos_P,  y_C = y_P + H(P),  level_C = level_P + H(P)/3
```

**Пол / рама пола / крыша ребром на верх стены** (`top → edge:m`):

По умолчанию внешняя нормаль ребра `m` ребёнка совпадает с нормалью стены,
то есть ребёнок лежит **над родительской ячейкой** стены. `flip: true`
кладёт его по другую сторону.

```
flip = false:  rot_C = rot_W − θ_m(C);         pos_C = pos_W − a_C · n(rot_W)
flip = true:   rot_C = rot_W + 180° − θ_m(C);  pos_C = pos_W + a_C · n(rot_W)
y_C = y_W + H(W),  level_C = level_W + H(W)/3
```

Для крыши `a_C` — апофема её формы, а `pos_C` — центр **проекции** крыши
на план. Высокое ребро крыши лежит на высоте `y_C + ROOF_RISE`.

**Лестница на ячейку** (`top → bottom`):

```
rot_S = rot_P + 90° · turns,  pos_S = pos_P,  y_S = y_P,  level_S = level_P
```

Лестница занимает всю ячейку и выводит на `level_P + 1`.

**Шкаф на ячейку** (`top`):

```
rot_T = rot_P + rotation
pos_T = pos_P + R(rot_P) · offset          // R — поворот вектора на угол
y_T   = y_P
```

**Дверь в проём** (`opening`): `pos`, `rot`, `y` равны проёму.
`hinge` — сторона петель, если смотреть снаружи по нормали проёма.

### 4.8 Соседство

После вычисления всех трансформов движок находит все пары сокетов,
совпадающих по положению (допуск 1 мм) и по высоте и имеющих
противоположные нормали (для рёбер) либо одинаковые позиции (для `top`
стены и ребра пола). Эти пары записываются в `resolved.adjacency`.
Именно по ним, а не по дереву `attach`, работают проверки стабильности и
подсчёт «сколько стен вокруг шкафа».

## 5. Элементы

```jsonc
{ "id": "f1", "kind": "square-foundation", "root": true }   // корень, один на документ

{
  "id": "w1",                 // обязательно
  "kind": "wall",             // обязательно, см. §4.4
  "grade": "stone",           // необязательно, иначе defaults.grade
  "attach": {                 // у всех, кроме корня
    "to": "f1",
    "socket": "edge:0",
    "selfSocket": "bottom",   // см. §4.5
    "flip": false,            // только top стены → пол/крыша
    "turns": 0                // только лестницы
  },
  "bunker": true,             // только крыши: крыша-затвор роф-бункера
  "label": "Фронт",           // необязательно, для UI
  "notes": "..."              // необязательно
}
```

Правила:

- `bunker: true` допустим только у `roof` и `roof-triangle`: это
  крыша-затвор роф-бункера. В игре она держится на дешёвой опоре,
  которую хозяин ломает изнутри, чтобы войти, а потом ставит опору и
  крышу заново. Для рейда это обычная крыша своего материала; в
  просмотре переключатель «Открыть двери» её убирает (стабильность не
  моделируется).

- У элемента ровно одно из полей `root: true` или `attach`.
- `root: true` допустим только у `square-foundation` и
  `triangle-foundation`, и ровно у одного элемента в документе. Это
  ячейка, на которой стоит шкаф; если шкафов несколько или шкаф стоит на
  верхнем этаже, корень — фундамент под ним. Шкаф не на корне — это
  предупреждение `W04`, а не ошибка.
- Отдельно стоящие части базы (вторая постройка, внешний периметр) в
  v1.0 не описываются: всё, что есть в документе, связано с корнем
  цепочкой `attach`.
- Порядок элементов в массиве не важен: движок строит дерево по ссылкам
  `attach.to` и обходит его от корня. Цикл ссылок или элемент, не
  достижимый от корня, — ошибка `V02`.

### Зарезервированные `kind` (не входят в v1.0)

`foundation-steps`, `ramp`, `half-floor`, `spiral-stairs`,
`spiral-stairs-triangle`. Валидатор v1.0 отклоняет их; в v1.1 они
добавятся в `ElementKind` без изменения остальных полей.

## 6. Объекты

```jsonc
{ "id": "tc1", "kind": "tool-cupboard",
  "attach": { "to": "f2", "socket": "top" },
  "offset": [0.8, 0.8], "rotation": 225 }

{ "id": "door1", "kind": "sheet-metal-door",
  "attach": { "to": "d1", "socket": "opening" },
  "hinge": "right", "opens": "outward", "open": false }
```

| `kind` | Куда ставится | Доп. поля |
|---|---|---|
| `tool-cupboard` | `top` фундамента или пола | `offset` [x, z] от центра ячейки, `rotation` |
| `wooden-door`, `sheet-metal-door`, `armored-door` | `opening` элемента `doorway` | `hinge`, `opens`, `open` |
| `garage-door`, `wooden-double-door`, `sheet-metal-double-door`, `armored-double-door` | `opening` элемента `wall-frame` | `opens`, `open` (`hinge` игнорируется: у двойной двери петли с обеих сторон, гаражная поднимается) |
| `strengthened-glass-window`, `reinforced-glass-window`, `metal-window-bars` | `opening` элемента `window-frame` | нет (`hinge`, `opens`, `open` игнорируются) |
| `drop-box` | `face` стены или половинной стены | `offset` [вдоль стены, высота] от середины низа стены, `direction` обязателен: `out` — передача изнутри наружу (по нормали стены), `in` — снаружи внутрь |

Поля дверей:

| Поле | Значения | По умолчанию | Смысл |
|---|---|---|---|
| `hinge` | `left`, `right` | `left` | Сторона петель, если смотреть снаружи по нормали проёма |
| `opens` | `outward`, `inward` | `outward` | Куда распахивается: по нормали проёма или против неё |
| `open` | boolean | `false` | Дверь показана открытой — для просмотра и для проверки, что перекрывает |

Схема запрещает `hinge`, `opens` и `open` у шкафа и дроп-бокса,
`offset`/`rotation` у дверей, `rotation` у дроп-бокса и `direction` у всех,
кроме дроп-бокса. Дроп-боксы в рейде не считаются: они не преграда и не
цель. Закатанный шкаф без двери обслуживается через пару дроп-боксов:
один `out`, другой `in`.

## 7. Слой `resolved`

```jsonc
"resolved": {
  "generator": "rust-calculator-geometry@1.0.0",
  "sourceHash": "sha256:…",             // хеш авторского слоя
  "elements": {
    "w1": { "position": [0.866, 0, 0], "rotation": 0, "level": 0,
            "sockets": { "top": { "position": [0.866, 3, 0], "normal": [1, 0] } } }
  },
  "deployables": { "tc1": { "position": [0, 0, 0], "rotation": 0, "level": 0 } },
  "adjacency": [
    { "a": { "id": "c1", "socket": "edge:1" }, "b": { "id": "w2", "socket": "top" } }
  ]
}
```

- `position` — мировые `[x, y, z]` центра элемента (для стены — середина
  нижнего ребра), округлённые до 0.001.
- `sockets` — необязательная карта мировых положений сокетов; `normal` —
  единичный вектор в плане `(x, z)`.
- `sourceHash` — SHA-256 от канонического JSON (ключи отсортированы, без
  пробелов) объекта `{ defaults, elements, deployables }`. Если хеш не
  совпадает с текущим авторским слоем, `resolved` считается устаревшим и
  пересчитывается; валидатор при этом выдаёт предупреждение `W01`, а не
  ошибку.
- Приложение сохраняет `resolved` в файл, чтобы чертёж можно было
  открыть в рендере без движка (например, в стороннем просмотрщике), но
  никогда не читает из него то, что можно вычислить заново.

## 8. Правила валидации

Два уровня. **Схема** проверяет форму документа (типы, обязательные
поля, enum, взаимоисключающие поля). **Валидатор** проверяет то, что
схемой не выразить. Каждая ошибка имеет код, `id` элемента и сообщение.

| Код | Уровень | Правило |
|---|---|---|
| `V01` | ошибка | `id` уникальны среди элементов и объектов |
| `V02` | ошибка | Ровно один элемент с `root: true`, и это фундамент; `attach.to` ссылается на существующий элемент; граф ссылок — дерево без циклов, все элементы достижимы от корня |
| `V03` | ошибка | `attach.socket` существует у типа родителя, `selfSocket` — у типа ребёнка (§4.4) |
| `V04` | ошибка | Пара сокетов разрешена матрицей совместимости (§4.5) |
| `V05` | ошибка | Слот сокета не занят дважды (§4.6) |
| `V06` | ошибка | Две ячейки одного уровня не совпадают и не пересекаются в плане (центры дальше 1 мм и полигоны не перекрываются) |
| `V07` | ошибка | Две стены-типа не занимают одно ребро на одном уровне |
| `V08` | ошибка | Над лестницей на `level + 1` либо пусто, либо `floor-frame` / `triangle-floor-frame` |
| `V10` | ошибка | Опора: стена-тип стоит на ребре ячейки или на `top` стены; пол на `level > 0` имеет хотя бы одно ребро на `top` стены или примыкает к опёртому полу (транзитивно); крыша низким ребром на `top` стены или на ребре ячейки. Упрощение реальной стабильности, см. ниже |
| `V11` | ошибка | Дверь соответствует проёму (§6); один проём — одна дверь |
| `V12` | ошибка | Шкаф целиком внутри ячейки: прямоугольник `TC_FOOTPRINT` после `offset`/`rotation` лежит в полигоне ячейки с отступом 0.1 м; шкафы не пересекаются |
| `W01` | предупреждение | `resolved.sourceHash` не совпадает с авторским слоем |
| `W02` | предупреждение | Шкаф не окружён со всех сторон: у ячейки шкафа есть ребро без стены-типа или без соседней ячейки, либо над ней нет пола |
| `W03` | предупреждение | Элемент `twig` в чертеже с `gameVersion` — напоминание, что twig не считается при рейде |
| `W04` | предупреждение | Шкаф стоит не на корневой ячейке |

**Про стабильность.** Игра считает стабильность процентами по цепочке
опор; `V10` заменяет это бинарной проверкой «есть ли опора». Этого
достаточно для планов из каменных и металлических блоков обычной формы.
Навесы длиной более двух полов от стены в игре не встанут, а `V10` их
пропустит; это известное ограничение v1.0.

Порядок: сначала схема, затем `V01`–`V05` (без геометрии), затем
вычисление `resolved`, затем `V06`–`V13` и предупреждения. Если
`V01`–`V05` дали ошибки, геометрия не считается.

### 9.3 Рейд

Стоимость пробития одного элемента берётся из `RAID_RULES[grade]`
(`src/data/raidData.ts`) — там уже лежат satchel / rocket / c4 /
explosiveAmmo / optimal для wood, stone, metal, armored. `twig`
взрывчаткой не считается (ломается инструментом) — для него все значения
`0`.

Двери и вставки в окна считаются по отдельной таблице (обновление 2026-09):

| `kind` | satchel | rocket | c4 | explosiveAmmo | optimal |
|---|---|---|---|---|---|
| `wooden-door`, `wooden-double-door` | 2 | 1 | 1 | 18 | explosiveAmmo 18 |
| `sheet-metal-door`, `sheet-metal-double-door` | 4 | 2 | 1 | 63 | explosiveAmmo 63 |
| `garage-door` | 9 | 3 | 2 | 150 | explosiveAmmo 150 |
| `armored-door`, `armored-double-door` | 15 | 5 | 3 | 250 | explosiveAmmo 250 |
| `strengthened-glass-window` | 9 | 3 | 2 | 140 | explosiveAmmo 140 |
| `reinforced-glass-window`, `metal-window-bars` | 12 | 4 | 2 | 200 | c4 2 |

`optimal` здесь — минимум серы при крафт-костах из `EXPLOSIVE_COSTS`
(explosive ammo 25, satchel 480, rocket 1400, c4 2200 серы): для всех
дверей это explosive ammo (гаражная: 150 × 25 = 3750 против 3 ракет =
4200). Как и для блоков, значение хранится в конфиге, а не вычисляется в UI.

Путь рейда в чертеже не хранится: приложение считает его на лету.

**Граф пространств.** Узел — пространство над ячейкой целого уровня:
над фундаментом, над полом, а если над ячейкой пола нет, но на её
стенах стоят стены следующего уровня, — виртуальное пространство
(комната без пола, как тамбур над запрыгом). Полы на половинной высоте
узлами не являются. Рёбра:

- между соседними пространствами одного уровня через общее ребро ячейки
  весят столько серы, сколько стоит сломать то, что на нём стоит
  выбранным методом: стена, половинная стена, проём с дверью, окно со
  вставкой; проём и рама без двери, пустая оконная рама и низкая стена
  бесплатны;
- ребро с «улицей», если у ребра ячейки нет соседа;
- вертикальное ребро в пространство над ним: через пол (стоимость пола,
  рама пола бесплатна) или бесплатно, если пола нет;
- пространство, над которым ничего нет, соединено с улицей бесплатно:
  это крыша;
- плита крыши (`roof`, `roof-triangle`) лежит над позицией ячейки,
  соседней с той, к ребру (или верху стены на этом ребре) которой она
  примыкает низким ребром: она закрывает это пространство сверху и
  стоит как стена своего материала, а её низкое ребро перекрывает ребро,
  к которому примыкает, если на нём нет стены-типа. Так крыша низким
  ребром на открытом ребре ячейки шкафа запирает вход (роф-бункер,
  §10.6); проход под скатом с боков считается свободным.

**Варианты и выбор одного.** Алгоритм Йена даёт несколько самых
дешёвых по штукам путей от улицы до пространства шкафа; каждый
пересчитывается планировщиком сплеша (§9.4), к ним добавляются залпы.
Для каждого варианта считается, какие замкнутые пространства становятся
достижимы с улицы после разрушения его элементов, и их суммарная
**ценность**: пространство со шкафом — 3, транзитные — запрыг (над
ячейкой пол на половинной высоте), комната без пола, аирлок (ровно две
двери и никаких других проходов) — 0.25 и 0.5, остальные — 1. Один
набор разрушений — один вариант, самый дешёвый по сере. Показывается
**один** вариант — результат симуляции по этапам (§9.4). Мягкая сторона
стен не учитывается.

### 9.4 Сплеш взрывчатки

Расчёт «по штукам» считает каждый элемент отдельно. Планировщик сплеша
считает взрывы в точках: один взрыв бьёт по всем элементам в радиусе с
падением урона по расстоянию до **ближайшей точки** элемента, поэтому
удар в угол плиты бьёт по всем плитам этого угла полностью.

| Взрывчатка | урон по блоку | урон по двери | по области | полный радиус | радиус сплеша | сера |
|---|---|---|---|---|---|---|
| ракета | ≈ 137.7 | ≈ 210 | да | ≈ 1.0 м | ≈ 3.8 м | 1400 |
| C4 | ≈ 275 | ≈ 350 | нет: только блок, на который поставлена | — | — | 2200 |
| разрывной патрон | wood 5.11, stone 2.70, metal 2.5, armored 2.5 | 3.97–11.1 по виду | да | ≈ 0.3 м | ≈ 0.6 м | 25 |
| сачель | wood 83.4, stone 50, metal 43.5 | 62.5–100 по виду | нет | — | — | 480 |

Урон подобран так, чтобы число единиц на блок совпадало с таблицей
рейда 2026-09; радиусы приближённые и подлежат замеру. Метод
«оптимально» разрешает ракеты, C4 и разрывные **вперемешку**: например,
C4 в каменную стену и разрывные на добивание дешевле двух C4.

**Симуляция по этапам.** Рейд считается как последовательность этапов.
На каждом этапе выбирается залп: точка на поверхности элемента, который
граничит с доступной рейдеру областью, взрывчатка и число единиц — одна
единица или столько, чтобы погиб первый элемент с учётом уже
накопленного урона. Урон от залпа получают все элементы в радиусе,
которые видны из точки взрыва. Погибшие элементы убираются **все
сразу**, доступная область и граница пересчитываются, и следующий этап
начинается уже с новой границы — так удар в угол крыши снимает все
примыкающие плиты одним этапом, а C4 в стену и разрывные на добивание
складываются в два этапа. Урон копится между этапами. Симуляция идёт до
тех пор, пока пространство шкафа не станет доступным.

Залп этапа выбирается по одной из трёх стратегий: «ценность» —
ценность открытых этим залпом пространств на единицу серы; «приближение»
— снижение остаточной цены до шкафа по штукам (с учётом накопленного
урона) на единицу серы; «разрушение» — число ломаемых конструкций на
единицу серы. Во всех стратегиях вторым критерием идёт число
конструкций, которые ломает залп: на каждом этапе ищется точка, ломающая
как можно больше. Этап допускается, только если он приближает к шкафу
(снижает остаточную цену) или открывает полноценную комнату (ценность
не ниже 1): дешёвые двери транзитных ячеек ради половины очка ценности в
план не попадают. Все симуляции доводятся до конца, показывается самая
дешёвая по сере; при равной цене — та, что открывает больше ценности,
затем та, что ломает больше, затем та, где удары ниже. Ценность не
перевешивает цену: план дороже ради лишних комнат — уже не рейд до
шкафа.

Крыша как цель и преграда — наклонная плита: своя система координат с
наклоном вокруг ребра, скат — полигон в ней, расчётная поверхность на
середине толщины, грань к рейдеру, как у плит. Сверху к ней подходят с
точки над скатом, из-под неё — из пространства под ним.

Точки удара не фиксированы: поверхность каждого элемента на границе
доступной области покрывается сеткой (центр, рёбра, углы и промежуточные
точки, у плиты — грань, обращённая к рейдеру), для каждой точки и
взрывчатки рассматриваются залпы в одну единицу и до каждого порога, на
котором гибнет очередной задетый элемент. Дорогая оценка (остаточная
цена через поиск пути) делается для лучших по дешёвому ключу
(открываемая ценность, приближение к шкафу по набору погибших и
полезный урон на серу, по группам «взрывчатка × класс залпа»; без
приближения в ключе одна ракета в деревянную дверь проигрывала бы отбор
залпам в угол стен), а лучшая точка затем дожимается локальным поиском вдоль
поверхности, чтобы в радиус попадало как можно больше плит и стен. Точки
сдвинуты к точке обзора рейдера (середина доступного пространства перед
элементом, с улицы — точка за ребром входа) и наружу вдоль поверхности. Точка должна быть
видна с точки обзора: если сдвиг наружу увёл её за преграду, берётся
сдвиг только к рейдеру, иначе точка отбрасывается.

**Преграды.** Сплеш доходит до элемента, только если отрезок от точки
взрыва до его ближайшей точки не пересекает целый элемент, включая саму
атакуемую дверь или стену: сквозь закрытую дверь соседей не достать.
**Правило контакта**: элемент, касающийся точки удара (его ближайшая
точка не дальше 15 см от точки на поверхности), задет и без прямой
видимости, если он открыт рейдеру — граничит с доступной областью — и
взрыв с той стороны, с которой к нему есть доступ. Так удар в угловую
колонну задевает все сходящиеся в ней открытые конструкции: крышу
коридора, его стену, внешнюю стену и стены этажа выше; но не проём,
скрытый за стеной, и не потолок, к которому рейдер стоит снизу.
Границы преград включающие, самый конец отрезка (поверхность цели)
соседней преградой не считается. Стены и двери в расчёте сплеша на 5 см
короче по высоте сверху и снизу, и как цели, и как преграды, а стены-цели
ещё и на 5 см уже с каждого торца: их рёбра не лежат на плоскости пола,
а торцы — на угловой колонне, поэтому взрыв на крыше не достаёт до стен
под плитами, взрыв на внешнем углу — до проёма за перпендикулярной
стеной, а низ стены, стоящей на крыше, не закрывает плиты вокруг неё.
Плиты как цели на 5 см уже стен (кромка внутрь от плоскости стены), а их
расчётная поверхность лежит в середине толщины плиты: снаружи кромку
потолка закрывает стена, и потолок нельзя сломать с улицы. Плиты одной
плоскости друг друга не закрывают — взрыв над ними достаёт все плиты
угла. Плита как преграда работает направленно: луч вниз сквозь её
плоскость она закрывает с запасом 5 см (швы между плитами закрыты и
с крыши внутрь не прострелить), а луч вверх, из-под уровня крыши к
стене над ней, не цепляет её кромкой (допуск 2 см). Фундаменты —
обычные цели сплеша: внутри соты удар в угол пола ломает и их, но
обрушение построенного на них в v1.0 не моделируется.

Пропановые бомбы и катапульта не считаются.

## 10. Примеры

### 10.1 Закатанный шкаф (`examples/sealed-triangle-tc.json`)

Треугольный каменный фундамент, три стены по рёбрам, треугольный пол на
верху первой стены, шкаф в дальнем углу, два дроп-бокса на стене `w1`
(`out` и `in`) — двери нет, лут передаётся через них. Ожидаемый
результат движка для элементов:

| id | position | rotation | как получено |
|---|---|---|---|
| `f1` | [0, 0, 0] | 0 | root |
| `w1` | [0.866, 0, 0] | 0 | `edge:0`: `a_tri · n(0°)` |
| `w2` | [−0.433, 0, 0.75] | 120 | `edge:1`: `0.866 · n(120°)` |
| `w3` | [−0.433, 0, −0.75] | 240 | `edge:2`: `0.866 · n(240°)` |
| `c1` | [0, 3, 0] | 0 | `top` w1 → `edge:0`, flip=false: `pos_w1 − 0.866 · n(0°)` |

Соседство: `c1.edge:1` ↔ `w2.top`, `c1.edge:2` ↔ `w3.top` — пол опёрт на
все три стены, хотя в `attach` указана только одна. `W02` не срабатывает:
ячейка шкафа закрыта со всех сторон и сверху. Дроп-боксы: позиция —
середина низа `w1` плюс смещение вдоль стены и по высоте, поворот равен
нормали стены.

### 10.2 Дом 2×1 с аирлоком (`examples/starter-2x1.json`)

Два квадратных фундамента: корневая ячейка со шкафом и тамбур-аирлок.
Внутренний проём у шкафа — `wall-frame` с двойной металлической дверью,
`opens: outward` (нормаль рамы смотрит в тамбур). Внешний одиночный
проём стоит на боковой стене тамбура в том же углу. Открытая двойная
дверь ложится поперёк прохода от наружной двери, поэтому в тамбур не
зайти, пока дверь у шкафа открыта. Сам факт перекрытия валидатор v1.0
не проверяет, это задача v1.1 (`W05`). Пример также показывает, что на
одном ребре `f1.edge:0` одновременно стоят сосед `f2` и проём `d_inner`
(два слота, §4.6) и `offset`/`rotation` шкафа.

### 10.3 Дом 2×2 с запрыгом (`examples/house-2x2.json`)

Классический 2×2 с входом через крышу. Первый этаж глухой: комната со
шкафом `f1` закрыта двойной дверью в `wall-frame`, за ней тамбур `f2` с
ещё одной двойной дверью, дальше `f3` с двойной дверью в ячейку
запрыга `f4`. В `f4` на полустене `hw1` лежит квадратный пол `m4` на
уровне 0.5 — он делит ячейку пополам по высоте; сверху `hw2` достраивает
стену до потолка. Над `f4` пола нет: с `m4` сразу попадают в тамбур 1×1
на втором этаже, стены которого стоят на стенах первого этажа
(`top → bottom`); из тамбура двойная дверь `d_roof` на крышу.
Пример показывает стопку полустен, пол на половинной высоте, уровни
0.5, 1 и 2 и виртуальное пространство тамбура без пола.

### 10.4 Шкаф в треугольнике с окном (`examples/triangle-tc-window.json`)

Треугольный фундамент, две стены и `window-frame` с укреплённым
стеклом (`strengthened-glass-window` в `opening`), шкаф в дальнем углу
фронтом к окну. Самый дешёвый рейд идёт через стекло: 140 explosive
ammo дешевле двух C4 в стену.

### 10.5 Бункер на 30 ракет (`examples/bunker-30-rockets.json`)

База, спроектированная под расчёт рейда: бронированное ядро со шкафом
без дверей, вокруг бронированная сота 3×3, над всей сотой второй этаж с
бронированными стенами и крышей, все потолки бронированные. Любой путь
к шкафу пересекает два бронированных слоя: снаружи в соту (15 ракет) и
из соты в ядро (15), сверху — крыша (15) и потолок ядра (15). Вход для
хозяина — коридор из трёх ячеек с четырьмя бронированными дверями:
4 × 5 ракет до соты плюс 15 до ядра, то есть дороже стены. Шкаф закатан:
лут передаётся через два дроп-бокса на стене ядра `cw0`, `out` и `in`. Симуляция
подтверждает: 30 ракет, 29 не хватит. Первая версия примера с комнатой
над ядром размером в одну ячейку держала только 15: угол потолка ядра
выходил на крышу соты, и залп в этот угол снимал его снаружи.

В 3D-просмотре переключатели «Материал» и «Двери» (иконками, как в
разделе строительства) всегда применяются поверх чертежа перед
проверкой схемой, по умолчанию камень и металлические двери: материал
заменяет `grade` у всех элементов, тип дверей заменяет одиночные двери на
выбранный вид, а двойные — на двойные того же вида или гаражные. Расчёт
рейда идёт уже по изменённому чертежу; бункер из §10.5 держит 30 ракет
при выборе МВК.

### 10.6 Роф-бункер на треугольнике (`examples/roof-bunker.json`)

Шкаф в каменном треугольнике без двери: две стены, потолок, а третье
ребро закрыто плитой крыши `rb` (`bunker: true`), поставленной на него
низким ребром. Крыша лежит над квадратным тамбуром `f2` с боковыми
стенами и дверью в дальнем проёме: под скатом у самого треугольника
прохода нет, а сверху тамбур закрыт самой крышей. В игре такую крышу
держит дешёвая опора; хозяин ломает её изнутри, крыша падает, вход
открыт, после чего опора и крыша ставятся заново. Рейд считает крышу
обычной каменной плитой: два C4 в неё — столько же, сколько в стену
треугольника, а оптимально (C4 и разрывные) — 4 300 через стену
ячейки шкафа. В просмотре переключатель «Открыть двери» роняет
крышу-затвор, показывая открытый бункер.

Все шесть примеров предзагружены в разделе «3D-просмотр» приложения;
туда же можно загрузить любой документ этого формата. Переключатель
«Открыть двери» (или `?doors=open` в адресе) показывает все двери
распахнутыми по их `opens` и убирает крыши-затворы.

## 11. Как проверить документ

Схема — draft 2020-12, поэтому нужен Ajv 8 с `ajv/dist/2020`:

```bash
npm i -D ajv ajv-formats
node -e '
  const Ajv = require("ajv/dist/2020"); const addFormats = require("ajv-formats");
  const ajv = addFormats(new Ajv({ strict: true, strictRequired: false }));
  const v = ajv.compile(require("./docs/blueprint/schema/blueprint.schema.json"));
  const ok = v(require("./docs/blueprint/examples/starter-2x1.json"));
  console.log(ok || v.errors);'
```

Оба примера проходят схему; документы с `root` и `attach` одновременно,
со стеной в роли корня, с дверью на `top`, с `hinge` у шкафа и с сокетом
`edge:5` схемой отклоняются (проверено при написании спецификации).
Единственность корня схема не выражает, это `V02`.

## 12. Версионирование

- `formatVersion` меняется по semver в рамках `major.minor`.
- **minor** — только добавление: новые `kind`, новые необязательные поля,
  новые коды валидации. Документ v1.0 остаётся валидным для v1.1.
- **major** — изменение смысла существующих полей, например другая
  нумерация рёбер. Требует миграции.
- Движок геометрии указывает свою версию в `resolved.generator`; при
  изменении констант §4.2 версия движка растёт, формат — нет.

## 13. Что сознательно не вошло в v1.0

- Печи, ящики, турели, ловушки, ставни и амбразуры в `window-frame`,
  внешние стены, электрика. Для них зарезервирован массив `deployables` с новыми `kind`.
- Ступени, рамп, половинный пол, спиральные лестницы — зарезервированные
  `kind`, см. §5.
- Точная модель стабильности игры (проценты), см. `V10`.
- Террейн и перепады высот между фундаментами: все фундаменты одного
  документа лежат на одной плоскости.
- Отдельно стоящие постройки: один документ — одна связная база с одним
  корнем. Если понадобится, в v1.x у корня появится необязательное
  смещение относительно корня другого документа.
