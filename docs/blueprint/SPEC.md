# Rust Base Blueprint — спецификация формата v2.0

Формат JSON-документа, описывающего постройку в Rust: строительные блоки
с их положением в мире, шкаф (Tool Cupboard), двери и другие объекты на
блоках. Документы прежнего формата 1.0 читаются и переводятся в 2.0
(§12). Документ предназначен для
приложения-конструктора в этом репозитории: по нему считается геометрия,
проверяется корректность постройки, рисуется 3D и считаются стоимость
постройки, апкипа и рейда.

Состав:

| Файл | Назначение |
|---|---|
| `docs/blueprint/SPEC.md` | этот документ |
| `docs/blueprint/schema/blueprint.schema.json` | формальная JSON Schema (draft 2020-12) |
| `docs/blueprint/examples/*.json` | проверенные схемой примеры |

Данные игры в документе сверены с обновлением **2026-09** (Breach and Clear).
Числа игры меняются ежемесячно, поэтому каждый чертёж хранит `meta.gameVersion`.

---

## 1. Принципы

1. **Позы, как в игре.** Каждый элемент хранит свою позу в мире —
   `position` и `rotation`, — как сущность на сервере игры. Связи между
   блоками в документе не хранятся: два блока соединены, если совпадают
   их сокеты (§4.8), и стабильность считается по геометрии. В игре здание
   — это компонента связности блоков, а не дерево от корня, поэтому корня
   в формате нет и начало координат ничем не выделено. Сокеты и формулы
   §4 нужны редактору: блок, поставленный в сокет соседа, получает позу
   по формулам §4.7, и в документ записывается уже готовая поза.
   Объекты (шкаф, двери, вставки в окна, дроп-боксы) крепятся к элементу
   через `attach`, как дочерние сущности в игре.
2. **Два слоя.** Авторский слой (`elements`, `deployables`) — источник
   истины, его пишут люди и ИИ. Вычисляемый слой (`resolved`) — результат
   работы движка геометрии: позы элементов копируются из документа, позы
   объектов вычисляются по `attach`. Он никогда не редактируется руками и
   пересчитывается при любом изменении авторского слоя.
3. **Один каталог.** Идентификаторы типов блоков (`kind`) совпадают с `id`
   из `src/data/blocks.ts`, поэтому расчёт стоимости и апкипа работает
   напрямую по чертежу без таблиц соответствия.
4. **Детерминизм.** Один и тот же авторский слой всегда даёт один и тот же
   `resolved` с точностью до округления до 1 мм.
5. **YAGNI.** В формат входят только блоки строительного плана, шкаф,
   двери, вставки в окна и дроп-боксы. Всё остальное (печи, ящики,
   турели, электрика, внешние стены) добавляется в минорных версиях 2.x
   без изменения существующих полей.

## 2. Термины

| Термин | Значение |
|---|---|
| Элемент (element) | Строительный блок из строительного плана: фундамент, стена, пол, лестница, крыша. Имеет `grade`. |
| Объект (deployable) | Размещаемый предмет: шкаф, дверь. Не имеет `grade`, материал зашит в `kind`. |
| Ячейка (cell) | Площадь, занимаемая фундаментом или полом: квадрат 3×3 м или равносторонний треугольник со стороной 3 м. |
| Поза (pose) | Положение элемента в мире: `position` [x, y, z] и `rotation` — угол вокруг вертикали (§4.1). Хранится в документе у каждого элемента. |
| Сокет (socket) | Именованная точка крепления на элементе. Соединение — пара совпадающих сокетов двух блоков; в документе 2.0 соединения элементов не записываются, они следуют из поз (§4.8). Объект указывает сокет элемента, на котором стоит (`attach`). |
| Здание | Блоки, связанные совпадающими сокетами, — компонента связности, как в игре. Корня у здания нет. |
| Уровень (level) | Этаж, `level = y / 3`. `0` — плоскость фундаментов на земле, `1` — на высоте полной стены (3 м). Половинные стены дают уровни с шагом `0.5`. |
| Grade | Материал блока: `twig`, `wood`, `stone`, `metal`, `armored`. |

## 3. Структура документа

```jsonc
{
  "$schema": "../schema/blueprint.schema.json",   // необязательно
  "formatVersion": "2.0",                          // обязательно: "2.0" или "1.0" (§12)
  "meta": { ... },                                 // обязательно
  "defaults": { "grade": "stone" },                // необязательно
  "elements": [ ... ],                             // обязательно, ≥ 1, у каждого поза
  "deployables": [ ... ],                          // необязательно
  "resolved": { ... }                              // необязательно, генерируется
}
```

Схема принимает `formatVersion` `"2.0"` и `"1.0"`. От версии зависит
форма элементов: в 2.0 это `Element` с позой (§5), в 1.0 — `LegacyElement`
с `root`/`attach`. Смешивать их в одном документе нельзя. Документ 1.0 при
загрузке переводится в 2.0 (§12).

### 3.1 `meta`

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `name` | string ≤ 120 | да | Название чертежа |
| `description` | string | нет | Произвольное описание |
| `author` | string | нет | Автор |
| `createdAt` | date-time | нет | ISO 8601 |
| `gameVersion` | string | нет | Месяц обновления игры, например `"2026-09"` |
| `tags` | string[] | нет | Уникальные теги |

### 3.2 `defaults`

`defaults.grade` — материал для элементов без собственного `grade`.
Если ни `defaults.grade`, ни `element.grade` не заданы, движок
использует `twig` (как в игре при установке блока).

### 3.3 Идентификаторы

`id` — строка по шаблону `^[a-z][a-z0-9_-]{0,63}$`, уникальна в пределах
документа среди элементов **и** объектов вместе.

## 4. Геометрический справочник

### 4.1 Система координат

- Единицы — метры, углы — градусы.
- Ось **Y** направлена вверх. Плоскость **(x, z)** — горизонтальная «планировка».
- Угол `θ` в плоскости отсчитывается от оси `+x` к оси `+z`:
  направление с углом `θ` равно `(cos θ, sin θ)` в координатах `(x, z)`.
- `rotation` элемента — угол его локальной оси `+x` в мировой плоскости.
  Все повороты в документе кратны 30°, поэтому движок сравнивает углы по
  модулю 360 с допуском 0.01°.
- Для Three.js (правая система, Y вверх) мировой угол вокруг оси Y равен
  `−θ`. Это единственное место, где знак меняется; формат сам по себе
  от рендера не зависит.

Оси — как в Unity: `position` элемента записан в мировых `[x, y, z]`,
`y` вверх. Начало координат ничем не выделено: редактор ставит первый
фундамент пустого участка в `[0, 0, 0]` с `rotation = 0`, но документ
может начинаться где угодно. У фундамента `y` — высота его верха над
землёй, допустимы 0, 1.5 и 3 м (`V12`). Уровень `level = y / 3`.
Перепады рельефа формат не описывает (см. §13).

### 4.2 Размеры блоков

Константы движка геометрии. Значения, помеченные `≈`, взяты из
наблюдений, а не из файлов игры; они вынесены в одну таблицу констант,
чтобы их можно было уточнить без изменения формата.

| Константа | Значение | Комментарий |
|---|---|---|
| `GRID` | 3.000 м | сторона квадратной ячейки и любого ребра |
| `SQ_APOTHEM` | 1.500 м | от центра квадрата до середины ребра |
| `SQ_CIRCUM` | 2.121 м | от центра квадрата до вершины |
| `TRI_APOTHEM` | 0.866 м | от центра треугольника до середины ребра (`3 / (2√3)`) |
| `TRI_CIRCUM` | 1.732 м | от центра треугольника до вершины (`3 / √3`) |
| `TRI_HEIGHT` | 2.598 м | высота треугольной ячейки |
| `WALL_H` | 3.000 м | стена, проём, оконная рама, рама стены |
| `HALF_WALL_H` | 1.500 м | половинная стена |
| `LOW_WALL_H` | ≈ 1.000 м | низкая стена |
| `ROOF_RISE` | ≈ 3.000 м | подъём крыши от низкого ребра до высокого |
| `FLOOR_T` | ≈ 0.200 м | толщина пола (только для рендера, на сокеты не влияет) |
| `DOORWAY_W × DOORWAY_H` | ≈ 1.3 × 2.2 м | проём `doorway`, одиночная дверь заполняет его целиком |
| `FRAME_W × FRAME_H` | ≈ 2.7 × 2.85 м | проём `wall-frame`: тонкая рамка, гаражная дверь заполняет его целиком |
| `DOUBLE_LEAF_H` | ≈ 2.3 м | высота створок двойной двери; выше — неподвижная часть до верха проёма |
| `WINDOW_W × WINDOW_H`, `WINDOW_SILL` | ≈ 2.2 × 1.3 м, подоконник 0.95 м | проём `window-frame` почти во всю ширину стены; точных чисел в открытых источниках нет, взяты пропорции модели |
| `TC_W × TC_D × TC_H` | ≈ 1.1 × 0.6 × 1.9 м | габарит шкафа: ширина вдоль стены, глубина, высота |

### 4.3 Локальная геометрия ячеек

В локальной системе ячейки центр — в начале координат, `rotation = 0`.
Ребро `edge:k` задаётся углом внешней нормали `θₖ`:

| Форма | `θₖ` | Апофема `a` | Вершины |
|---|---|---|---|
| квадрат | `90° · k`, k = 0..3 | 1.500 | на углах `45° + 90°·k`, радиус 2.121 |
| треугольник | `120° · k`, k = 0..2 | 0.866 | на углах `60° + 120°·k`, радиус 1.732 |

Центр ребра `k`: `a · (cos θₖ, sin θₖ)`. Ребро `edge:0` у обеих форм
смотрит в локальный `+x`.

### 4.4 Сокеты по типам элементов

| `kind` | Форма | Сокеты | Роль сокетов |
|---|---|---|---|
| `square-foundation` | квадрат | `edge:0..3`, `top` | рёбра принимают соседние ячейки и стены; `top` — лестницы и объекты |
| `triangle-foundation` | треугольник | `edge:0..2`, `top` | то же |
| `square-floor` | квадрат | `edge:0..3`, `top` | пол крепится **ребром** к `top` стены, к высокому ребру квадратной крыши или к ребру соседней ячейки; `top` — лестницы, съезд и ступени (сокет игры `Block`) и объекты |
| `triangle-floor` | треугольник | `edge:0..2`, `top` | то же |
| `floor-frame` | квадрат | `edge:0..3`, `top` | как пол; `top` не принимает ни объекты, ни лестницы, ни съезд (у рамы в игре нет сокетов `Block` и `Stairs`) |
| `triangle-floor-frame` | треугольник | `edge:0..2`, `top` | то же |
| `wall`, `half-wall` | ребро | `bottom`, `top`, `face` | `bottom` ставится на ребро ячейки или на `top` другой стены; `top` принимает рёбра полов и крыш и `bottom` стен; `face` — грань стены, принимает дроп-боксы |
| `low-wall` | ребро | `bottom`, `top` | как стена, без `face`; `top` ничего не принимает — у низкой стены в игре нет «мам» |
| `doorway` | ребро | `bottom`, `top`, `opening` | как стена; `opening` принимает одинарную дверь |
| `window-frame` | ребро | `bottom`, `top`, `opening` | как стена; `opening` принимает вставку в окно: стекло или решётку |
| `wall-frame` | ребро | `bottom`, `top`, `opening` | как стена; `opening` принимает гаражную и двойные двери |
| `stairs-l-shape`, `u-shaped-stairs` | ячейка | `bottom` | ставится на `top` квадратного фундамента или пола (не рамы), `turns` — поворот |
| `spiral-stairs` | ячейка | `bottom`, `top` | как лестница; высота марша 1,5 м, `top` принимает следующую винтовую лестницу |
| `roof` | квадрат | `edge:0` (низкое), `edge:1`, `edge:3` (боковые), `edge:2` (высокое) | `edge:0` ставится на `top` стены, на ребро ячейки или на `edge:2` другой крыши; боковые принимают соседние крыши; `edge:2` (сокеты игры `wall-female` и `floor-female` на высоте 3 м) принимает стены, рёбра полов и низкие рёбра крыш, по обе стороны (`flip`) |
| `roof-triangle` | треугольник | `edge:0` (низкое), `edge:1`, `edge:2` | как `roof`, вершина напротив `edge:0` поднята. Две треугольные крыши одного грейда в ряд (смотрят в одну сторону, основания вплотную) сами закрывают просвет между собой перевёрнутым треугольником в той же плоскости — условная модель игры `roof.straight.right` (RoofRight, угол 0, форма «треугольник») |
| `ramp`, `foundation-steps` | квадрат | `edge:0`, `edge:2`, `bottom` | `edge:0` (сокет игры `ramp-male`) ставится на ребро **фундамента** или на `edge:2` другого съезда или ступеней — блок занимает соседнюю клетку и спускается на 0,75 м (съезд) или 1,5 м (ступени); `edge:2` — нижний край (`ramp-female`); `bottom` ставится на `top` квадратного фундамента или пола, блок занимает эту клетку и поднимается от её верха, `turns` — поворот. У съезда на `top` две высоты, как в игре: `rise` 0 — `block-male` на `block-female`, низкий съезд с подъёмом 0,75 м; `rise` 0.75 — `misc-male` на `misc-female`, высокий съезд с подъёмом 1,5 м (модель выбирают `RampLow`/`RampHigh`); в рейде не участвует |

Сокеты объектов: шкаф занимает `top` ячейки, двери и вставки занимают
`opening`, дроп-боксы вешаются на `face` стены (на одной стене их может
быть несколько, по разным смещениям).

### 4.5 Матрица совместимости

Матрица описывает, какой сокет блока-хозяина принимает какой блок. По
ней редактор перебирает варианты установки нового блока в сокеты соседей
(`candidatePlacements` в `src/blueprint/editor.ts`), а при переводе
документа 1.0 проверяются его `attach` (`V03`, `V04`). В документе 2.0
сокеты элементов не записываются. Поля `attach.*` ниже — описание одного
варианта установки (тот же объект `Attach`, что у элемента 1.0).

Строка — сокет хозяина (`attach.socket`), столбец — тип и сокет
ставящегося блока (`attach.selfSocket`). Пусто — соединение запрещено.

| Родитель → Ребёнок | фундамент `edge` | пол / рама пола `edge` | стена-тип `bottom` | лестница `bottom` | съезд, ступени `edge:0` | съезд, ступени `bottom` | крыша `edge:0` | крыша `edge:1/3` | шкаф | дверь |
|---|---|---|---|---|---|---|---|---|---|---|
| фундамент `edge` | ✔ | | ✔ | | ✔ | | ✔ | | | |
| фундамент `top` (квадрат) | | | | ✔ | | ✔ | | | ✔ | |
| пол / рама `edge` | | ✔ | ✔ | | | | ✔ | | | |
| пол `top` (квадрат) | | | | ✔ | | ✔ | | | ✔ | |
| рама пола `top` | | | | | | | | | | |
| стена-тип `top` (кроме низкой стены) | | ✔ | ✔ | | | | ✔ | | | |
| винтовая лестница `top` | | | | винтовая | | | | | | |
| съезд, ступени `edge:2` | | | | | ✔ | | | | | |
| крыша `edge:2` (квадрат) | | ✔ | ✔ | | | | ✔ | | | |
| крыша `edge:1/3` | | | | | | | | ✔ | | |
| `doorway.opening` | | | | | | | | | | одинарная |
| `wall-frame.opening` | | | | | | | | | | гаражная, двойная |
| `window-frame.opening` | | | | | | | | | | стекло, решётка |

Фундаменты крепятся только к рёбрам фундаментов. Как в игре (у
фундамента три ряда боковых сокетов `foundation-top/mid/bot` с шагом
1.5 м), сосед может стоять выше или ниже: `attach.rise` — сдвиг в метрах
(−3, −1.5, 0, 1.5, 3), а верх любого фундамента должен быть на земле, на
высоте полустены или стены: 0, 1.5 или 3 м (иначе ошибка `V12`). Поднятый
фундамент рисуется до земли; в графе рейда пространство над ним — узел
своего уровня, полы над ним считаются этажами от его верха. «Стена-тип» — `wall`, `half-wall`,
`low-wall`, `doorway`, `window-frame`, `wall-frame`. Одинарные двери: `wooden-door`, `sheet-metal-door`,
`armored-door`. Двойные: `wooden-double-door`, `sheet-metal-double-door`,
`armored-double-door`.

`selfSocket` можно опустить, если у ребёнка ровно один подходящий сокет
(стены, лестницы, объекты). Для ячеек и крыш `selfSocket` обязателен.

Фундамент, поставленный на пустой участок, ни к чему не крепится, но его
рёбра и `top` — такие же сокеты, как у любой другой ячейки.

### 4.6 Ёмкость сокетов

| Сокет | Слоты |
|---|---|
| `edge` ячейки | один **сосед** (ячейка), одна **крыша** низким ребром (лежит над позицией соседа) и одна **стена-тип** одновременно |
| `top` ячейки | одна лестница **или** любое число объектов, не пересекающихся в плане |
| `top` стены-типа | **с каждой стороны** один пол (или рама) и одна крыша (крыша над полом — чердак) и одна стена сверху |
| `opening` | одна дверь |
| `edge:1/3` крыши | одна крыша |

Редактор не предлагает вариант, место которого уже занято. В документе
2.0 занятость проверяется по геометрии (функция `clash`, ошибка `V05`,
§8); в документе 1.0 при переводе два элемента, попавшие в один слот,
тоже дают `V05`.

### 4.7 Формулы размещения

Формулы описывают, как редактор вычисляет позу блока, поставленного в
сокет соседа: функция `socketPose` в `src/blueprint/geometry.ts`. Ею же
документ 1.0 разворачивается в позы при переводе. В документ 2.0
записывается результат: `position` с округлением до 1 мм, `rotation` по
модулю 360 и, у треугольной крыши, приставленной боком к
неперевёрнутой треугольной крыше, `inverted: true`. Формулы шкафа и
двери (в конце раздела) движок применяет к объектам при каждом
вычислении `resolved`.

Обозначения: `P` — хозяин (сокет которого принимает блок), `C` — новый блок, `pos` — центр в плане `(x, z)`,
`y` — высота, `rot` — поворот, `n(θ) = (cos θ, sin θ)`, `θₖ` — локальная
нормаль ребра `k`, `a` — апофема.

**Ячейка ребром к ребру ячейки** (`edge → edge`):

```
rot_C = rot_P + θ_k(P) + 180° − θ_m(C)
pos_C = pos_P + (a_P + a_C) · n(rot_P + θ_k(P))
y_C   = y_P,  level_C = level_P
```

**Стена-тип на ребро ячейки** (`edge → bottom`):

```
rot_W = rot_P + θ_k(P)            // нормаль стены смотрит наружу от P
pos_W = pos_P + a_P · n(rot_W)
y_W   = y_P,  level_W = level_P
```

**Стена-тип на верх стены-типа** (`top → bottom`, стопка):

```
rot_C = rot_P,  pos_C = pos_P,  y_C = y_P + H(P),  level_C = level_P + H(P)/3
```

**Пол / рама пола / крыша ребром на верх стены** (`top → edge:m`):

По умолчанию внешняя нормаль ребра `m` ребёнка совпадает с нормалью стены,
то есть ребёнок лежит **над родительской ячейкой** стены. `flip: true`
кладёт его по другую сторону.

```
flip = false:  rot_C = rot_W − θ_m(C);         pos_C = pos_W − a_C · n(rot_W)
flip = true:   rot_C = rot_W + 180° − θ_m(C);  pos_C = pos_W + a_C · n(rot_W)
y_C = y_W + H(W),  level_C = level_W + H(W)/3
```

Для крыши `a_C` — апофема её формы, а `pos_C` — центр **проекции** крыши
на план. Высокое ребро крыши лежит на высоте `y_C + ROOF_RISE`.

**Лестница на ячейку** (`top → bottom`):

```
rot_S = rot_P + 90° · turns,  pos_S = pos_P,  y_S = y_P,  level_S = level_P
```

Лестница занимает всю ячейку и выводит на `level_P + 1`.

**Шкаф на ячейку** (`top`):

```
rot_T = rot_P + rotation
pos_T = pos_P + R(rot_P) · offset          // R — поворот вектора на угол
y_T   = y_P
```

**Дверь в проём** (`opening`): `pos`, `rot`, `y` равны проёму.
`hinge` — сторона петель, если смотреть снаружи по нормали проёма.

### 4.8 Соседство

После вычисления всех трансформов движок находит все пары сокетов,
совпадающих по положению (допуск 1 мм) и по высоте и имеющих
противоположные нормали (для рёбер) либо одинаковые позиции (для `top`
стены и ребра пола). Эти пары записываются в `resolved.adjacency`.
Других связей между элементами в документе 2.0 нет: по совпадающим
сокетам работает стабильность (§11.1).

## 5. Элементы

```jsonc
{ "id": "f1", "kind": "square-foundation", "position": [0, 0, 0], "rotation": 0 }

{
  "id": "d_inner",            // обязательно
  "kind": "wall-frame",       // обязательно, см. §4.4
  "position": [1.5, 0, 0],    // обязательно: мировые [x, y, z], м, y вверх
  "rotation": 0,              // обязательно: градусы вокруг вертикали, §4.1
  "grade": "metal",           // необязательно, иначе defaults.grade
  "inverted": true,           // только треугольная крыша: перевёрнута
  "bunker": true,             // только крыши и полы: деталь затвора роф-бункера
  "label": "Внутренний проём",// необязательно, для UI
  "notes": "..."              // необязательно
}
```

Поза в документе — та же, что получает блок при установке в сокет
соседа (§4.7):

| Элемент | `position` | `rotation` |
|---|---|---|
| фундамент, пол, рама пола | центр ячейки; `y` — верх ячейки | поворот ячейки: её ребро `edge:0` смотрит по углу `rotation` |
| стена-тип | середина нижнего ребра; `y` — низ стены | угол нормали стены |
| крыша | центр проекции на план; `y` — высота низкого ребра | угол нормали низкого ребра `edge:0` |
| лестница | центр ячейки, на которой стоит; `y` — верх ячейки | поворот ячейки плюс `90° · turns` |
| съезд, ступени | по `socketPose` (§4.4): от ребра фундамента или верха ячейки | по `socketPose` |

Правила:

- `position` и `rotation` обязательны у каждого элемента. Полей `root` и
  `attach` у элемента 2.0 нет, схема их отклоняет.
- Связи между элементами не записываются: они следуют из совпадения
  сокетов (§4.8), как в игре. Держится ли блок, решает стабильность
  (§11.1); валидатор опору не проверяет.
- Место, которое занимает блок, не должно быть занято другим (`V05`,
  §8). Порядок элементов в массиве на геометрию не влияет; ошибку `V05`
  получает тот из двух элементов, что стоит в массиве позже.
- Стена с `rotation` и стена с `rotation + 180°` на том же месте — одно и
  то же ребро; разворот стены киянкой меняет только сторону нормали
  (§11.1).
- `inverted: true` имеет смысл только у `roof-triangle`: крыша
  перевёрнута, ребро `edge:0` у конька, вершина у края. Так она закрывает
  просвет между соседними треугольными крышами. Редактор выставляет флаг
  сам (§4.7).
- `bunker: true` допустим только у крыш и полов: это детали затвора
  роф-бункера — крыша-затвор и твиговая плита-опора под ней (§10.6). В
  игре хозяин ломает опору изнутри, крыша теряет стабильность и падает,
  а потом ставит опору и крышу заново. Для рейда это обычные элементы
  своего материала; в просмотре переключатель «Открыть двери» их
  убирает.
- Фундамент стоит на земле: верх на высоте 0, 1.5 или 3 м (`V12`).

### Зарезервированные `kind` (не входят в 2.0)

`half-floor`,
`spiral-stairs-triangle`. Схема 2.0 их отклоняет; в одной из минорных
версий 2.x они добавятся в `ElementKind` без изменения остальных полей.

## 6. Объекты

```jsonc
{ "id": "tc1", "kind": "tool-cupboard",
  "attach": { "to": "f2", "socket": "top" },
  "offset": [0.8, 0.8], "rotation": 225 }

{ "id": "door1", "kind": "sheet-metal-door",
  "attach": { "to": "d1", "socket": "opening" },
  "hinge": "right", "opens": "outward", "open": false }
```

| `kind` | Куда ставится | Доп. поля |
|---|---|---|
| `tool-cupboard` | `top` фундамента или пола | `offset` [x, z] от центра ячейки, `rotation` |
| `wooden-door`, `sheet-metal-door`, `armored-door` | `opening` элемента `doorway` | `hinge`, `opens`, `open` |
| `garage-door`, `wooden-double-door`, `sheet-metal-double-door`, `armored-double-door` | `opening` элемента `wall-frame` | `opens`, `open` (`hinge` игнорируется: у двойной двери петли с обеих сторон, гаражная поднимается) |
| `strengthened-glass-window`, `reinforced-glass-window`, `metal-window-bars`, `metal-embrasure` | `opening` элемента `window-frame` | нет (`hinge`, `opens`, `open` игнорируются) |
| `drop-box` | `face` стены или половинной стены | `offset` [вдоль стены, высота] от середины низа стены, `direction` обязателен: `out` — передача изнутри наружу (по нормали стены), `in` — снаружи внутрь |

Поля дверей:

| Поле | Значения | По умолчанию | Смысл |
|---|---|---|---|
| `hinge` | `left`, `right` | `left` | Сторона петель, если смотреть снаружи по нормали проёма |
| `opens` | `outward`, `inward` | `outward` | Куда распахивается: по нормали проёма или против неё |
| `open` | boolean | `false` | Дверь показана открытой — для просмотра и для проверки, что перекрывает |

Схема запрещает `hinge`, `opens` и `open` у шкафа и дроп-бокса,
`offset`/`rotation` у дверей, `rotation` у дроп-бокса и `direction` у всех,
кроме дроп-бокса. Дроп-боксы в рейде не считаются: они не преграда и не
цель. Пара дроп-боксов на одной стене (`out` и `in`) — способ передавать
лут в комнату без двери, как в ядре бункера §10.5. В просмотре дроп-бокс
рисуется ящиком сквозь стену, выступающим с обеих сторон, с короткой
стрелкой направления, которая начинается внутри ящика.

## 7. Слой `resolved`

```jsonc
"resolved": {
  "generator": "rust-calculator-geometry@1.0.0",
  "sourceHash": "sha256:…",             // хеш авторского слоя
  "elements": {
    "w1": { "position": [0.866, 0, 0], "rotation": 0, "level": 0,
            "sockets": { "top": { "position": [0.866, 3, 0], "normal": [1, 0] } } }
  },
  "deployables": { "tc1": { "position": [0, 0, 0], "rotation": 0, "level": 0 } },
  "adjacency": [
    { "a": { "id": "c1", "socket": "edge:1" }, "b": { "id": "w2", "socket": "top" } }
  ]
}
```

- Позы элементов в 2.0 движок не вычисляет, а копирует из документа:
  `position` — мировые `[x, y, z]` элемента в том же смысле, что в §5
  (для стены — середина нижнего ребра), округлённые до 0.001;
  `rotation` приводится к `[0, 360)` и округляется до 0.001;
  `level = y / 3`. Туда же переносятся `grade` (иначе `defaults.grade`,
  иначе `twig`), `inverted` и `bunker`.
- Позы объектов вычисляются по их `attach` от позы элемента-хозяина
  (§4.7: шкаф, дверь; дроп-бокс — смещение вдоль стены и по высоте).
- Для документа 1.0 позы элементов получаются обходом дерева `attach` от
  корня по `socketPose`; из них же строится документ 2.0 (§12).
- `sockets` — необязательная карта мировых положений сокетов; `normal` —
  единичный вектор в плане `(x, z)`.
- `sourceHash` — SHA-256 от канонического JSON (ключи отсортированы, без
  пробелов) объекта `{ defaults, elements, deployables }`. Если хеш не
  совпадает с текущим авторским слоем, `resolved` считается устаревшим и
  пересчитывается (предупреждение `W01`, см. §8).
- Поле `resolved` в файле нужно, чтобы чертёж можно было открыть в
  рендере без движка (например, в стороннем просмотрщике). Приложение
  его не читает: позы элементов уже есть в авторском слое, остальное
  вычисляется заново.

## 8. Правила валидации

Два уровня. **Схема** проверяет форму документа (типы, обязательные
поля, enum, взаимоисключающие поля). **Валидатор** проверяет то, что
схемой не выразить. Каждая ошибка имеет код, `id` элемента и сообщение.

Валидатор документа 2.0 — `resolveBlueprint` в `src/blueprint/geometry.ts`.

| Код | Уровень | Правило |
|---|---|---|
| `V01` | ошибка | `id` уникальны среди элементов и объектов |
| `V03` | ошибка | `kind` элемента известен каталогу (§4.4) |
| `V12` | ошибка | Верх фундамента на высоте 0, 1.5 или 3 м от земли: `position[1]` фундамента — одно из этих чисел |
| `V05` | ошибка | Место уже занято другим элементом (функция `clash`, правила ниже) |
| `V02` | ошибка | Объект: `attach.to` ссылается на существующий элемент |
| `V04` | ошибка | Объект стоит на подходящем сокете: шкаф — на `top` фундамента или пола (не рамы), дроп-бокс — на `face` стены или половинной стены (не проёма и не низкой стены), дверь и вставка — в `opening` проёма |
| `V11` | ошибка | Дверь или вставка соответствует проёму (§6); один проём — одна дверь |

**Занятость места (`V05`).** Каждый элемент сравнивается со всеми,
стоящими в массиве раньше; блоки, разнесённые больше чем на 6 м по
любой оси, не сравниваются. Место занято, если:

- **стены-типы** стоят на одном ребре — центры совпадают в плане (до
  1 см), повороты совпадают по модулю 180° (до 0.5°), — и их пролёты по
  высоте пересекаются: низ одинаковый или низ одной стены внутри высоты
  другой. Сторона нормали значения не имеет; стена, поставленная на верх
  другой, место не занимает;
- **ячейки** (фундаменты, полы, рамы пола, а также съезды и ступени)
  одного уровня (`y` совпадает до 1 см) пересекаются контурами в плане.
  Контуры усажены на 5 см, поэтому соседи по ребру не пересекаются;
- **фундамент** занимает столб от земли до своего верха: два
  фундамента с пересекающимися контурами конфликтуют на любой высоте,
  так же как фундамент и ячейка ниже его верха;
- **крыша** не уходит в фундамент: верх фундамента выше низкого ребра
  крыши, и контуры пересекаются;
- **две крыши** конфликтуют только как точный дубль: та же поза (до 1 см
  и 0.5°) и тот же `inverted`. С полами и стенами крыша не спорит (крыша
  над полом — чердак).

Порядок: сначала схема; для документа 1.0 — перевод в 2.0 (§12), и если
он дал ошибки, дальше проверка не идёт. Затем `V01`, затем по каждому
элементу `V03`, `V12`, `V05`, затем объекты (`V02`, `V04`, `V11`). При
любой ошибке `resolved` не возвращается.

**Чего в 2.0 нет.** Правила про корень и достижимость (`V02` для
элементов) и предупреждение `W04` «шкаф не на корне» убраны: в игре
здание — компонента связности, корня у него нет. Для документа 1.0
правила корня и дерева (`V02`–`V05` по `attach`) действуют при переводе
(§12). Прежние `V06` (пересечение ячеек) и `V07`
(две стены на ребре) вошли в `V05`. Бинарная проверка опоры `V10`
заменена расчётом стабильности как в игре (§11.1): блок ниже 5%
обрушивается в режиме стройки, валидатор опору не проверяет. `V08`
(что над лестницей), проверка габарита шкафа в ячейке и предупреждения
`W01`–`W03` (устаревший `resolved`, шкаф не окружён, twig в чертеже)
валидатор не выдаёт.

### 9.2 Стоимость постройки и апкип

Формулы игры, реализация — `src/blueprint/cost.ts`:

```
cost(block)   = baseCost(grade) × costMultiplier(kind)
build         = Σ cost(block) + Σ крафт объектов
rate(N)       = средняя ставка по брекетам от числа N облагаемых сущностей:
                первые 15 по 10 %, следующие 50 по 15 %, следующие 125 по 20 %, дальше 33.3 %
upkeep/сутки  = Σ cost(облагаемых) × rate(N)
```

`baseCost`: twig 50 wood, wood 200 wood, stone 300 stone, metal 200 metal
fragments, armored 25 HQM. `costMultiplier`: фундамент, стена, полустенка,
лестницы 1; дверной и оконный проём 0.7; треугольный фундамент, ступени,
рампа, низкая стена, рама стены, пол, рама пола, крыши 0.5; треугольный пол
и его рама 0.25.

Облагаются блоки, двери и вставки в окна (по цене крафта, без шестерёнок).
Шкаф и дроп-бокс входят только в стоимость постройки. Считается один
игрок, групповой множитель не учитывается. Панель справа показывает
стоимость, содержание в сутки и таблицу на 1, 2, 3, 5, 10, 15, 20, 25 и
30 суток.

| `sheet-metal-door` | 150 metal fragments | 250 |

| `garage-door` | 300 metal fragments + 2 gears | 600 |

### 9.3 Рейд

Стоимость пробития одного элемента берётся из `RAID_RULES[grade]`
(`src/data/raidData.ts`) — там уже лежат satchel / rocket / c4 /
explosiveAmmo / optimal для wood, stone, metal, armored. `twig`
взрывчаткой не считается (ломается инструментом) — для него все значения
`0`.

Двери и вставки в окна считаются по отдельной таблице (обновление 2026-09):

| `kind` | satchel | rocket | c4 | explosiveAmmo | optimal |
|---|---|---|---|---|---|
| `wooden-door`, `wooden-double-door` | 2 | 1 | 1 | 18 | explosiveAmmo 18 |
| `sheet-metal-door`, `sheet-metal-double-door` | 4 | 2 | 1 | 63 | explosiveAmmo 63 |
| `garage-door` | 9 | 3 | 2 | 150 | explosiveAmmo 150 |
| `armored-door`, `armored-double-door` | 15 | 5 | 3 | 250 | explosiveAmmo 250 |
| `strengthened-glass-window` | 9 | 3 | 2 | 140 | explosiveAmmo 140 |
| `reinforced-glass-window`, `metal-window-bars`, `metal-embrasure` | 12 | 4 | 2 | 200 | c4 2 |

`optimal` здесь — минимум серы при крафт-костах из `EXPLOSIVE_COSTS`
(explosive ammo 25, satchel 480, rocket 1400, c4 2200 серы): для всех
дверей это explosive ammo (гаражная: 150 × 25 = 3750 против 3 ракет =
4200). Как и для блоков, значение хранится в конфиге, а не вычисляется в UI.

Путь рейда в чертеже не хранится: приложение считает его на лету.

**Граф пространств.** Узел — пространство над ячейкой целого уровня:
над фундаментом, над полом, а если над ячейкой пола нет, но на её
стенах стоят стены следующего уровня, — виртуальное пространство
(комната без пола, как тамбур над запрыгом). Полы на половинной высоте
узлами не являются. Рёбра:

- между соседними пространствами одного уровня через общее ребро ячейки
  весят столько серы, сколько стоит сломать то, что на нём стоит
  выбранным методом: стена, половинная стена, проём с дверью, окно со
  вставкой; проём и рама без двери, пустая оконная рама и низкая стена
  бесплатны;
- ребро с «улицей», если у ребра ячейки нет соседа;
- вертикальное ребро в пространство над ним: через пол (стоимость пола,
  рама пола бесплатна) или бесплатно, если пола нет;
- пространство, над которым ничего нет, соединено с улицей бесплатно:
  это крыша;
- плита крыши (`roof`, `roof-triangle`) лежит над позицией ячейки,
  соседней с той, к ребру (или верху стены на этом ребре) которой она
  примыкает низким ребром: она закрывает это пространство сверху и
  стоит как стена своего материала, а её низкое ребро перекрывает ребро,
  к которому примыкает, если на нём нет стены-типа. Так крыша низким
  ребром на открытом ребре ячейки шкафа запирает вход (роф-бункер,
  §10.6); проход под скатом с боков считается свободным.

**Варианты и выбор одного.** Алгоритм Йена даёт несколько самых
дешёвых по штукам путей от улицы до пространства шкафа; каждый
пересчитывается планировщиком сплеша (§9.4), к ним добавляются залпы.
Для каждого варианта считается, какие замкнутые пространства становятся
достижимы с улицы после разрушения его элементов, и их суммарная
**ценность**: пространство со шкафом — 3, транзитные — запрыг (над
ячейкой пол на половинной высоте), комната без пола, аирлок (ровно две
двери и никаких других проходов) — 0.25 и 0.5, остальные — 1. Один
набор разрушений — один вариант, самый дешёвый по сере. Показывается
**один** вариант — результат симуляции по этапам (§9.4). Мягкая сторона
стен не учитывается.

### 9.4 Урон и сплеш — по правилам игры

Модель урона повторяет серверный код и данные клиента Rust
(`docs/research/rust-damage-mechanics.md`, числа — `src/blueprint/rustDamage.ts`).

**Урон по цели.** Для каждого типа урона заряда (Explosion, Blunt, Stab,
Bullet) `урон × (1 − защита)`; защита — ассет грейда (`blocktwig/wood/
stone/metal`, у МВК тот же `blockmetal`) или двери (`wooddoor` — от взрыва
−1, то есть вдвое; `metaldoor` 0.2). У стен, полов, фундаментов и крыш
сверху — «твёрдая сторона» `BuildingShell` (Bullet 0.5, Blunt/Stab 0.9,
Explosion 0): от сплеша она действует всегда, от посаженного заряда нет.
Здоровье: ветки 10, дерево 250, камень 500, металл 1000, МВК 2000; двери —
дерево 200, металл 250, гаражная 600, МВК 1000; стекло 350, решётки 500.

| Взрывчатка | урон заряда | радиус | как бьёт | сера |
|---|---|---|---|---|
| ракета | Explosion 275, Blunt 75 | полный до 1 м, ноль на 3.8 м | сплеш; центр взрыва — 0.39 м перед поверхностью | 1400 |
| C4 | Explosion 550 | — | посажена: весь урон блоку под ней | 2200 |
| сачель | Explosion 75, Blunt 200, Stab 200 | — | посажена, как C4 | 480 |
| разрывной патрон | пуля Bullet 50 + Explosion 0.01; радиальный Explosion 5 | 1.5 м, падение 1 − d/1.5 | блок под пулей — пуля и радиальный, остальные — радиальный | 25 |

Из этого получаются числа таблицы рейда: камень — 4 ракеты, 2 C4, 10
сачелей, 182 разрывных; металл — 8 / 4 / 23 / 400; МВК — 15 / 8 / 46 / 799;
металлическая дверь — 2 / 1 / 4 / 63.

**Сплеш.** Расстояние — от центра взрыва до ближайшей точки **коробки**
цели (bounds префаба: стена 0.2 × 3 × 3, пол 3 × 0.2 × 3, фундамент
2.8 × 2.8 до 2.8 м вниз, у крыши коробка ±4.4 м вдоль конька), урон ×
`1 − clamp01((d − rmin)/(r − rmin))`. Цель задета, если виден хотя бы
один из двух лучей — к центру её коробки или к ближайшей точке: луч не
должен упереться в чужой коллайдер раньше, чем войдёт в коробку цели.
Коллайдеры: стены и двери — коробки, проёмы — их рамы, полы, фундаменты и
крыши — призмы (рамы полов, низкие стены и лестницы не заслоняют).
Каждая цель получает урон от взрыва один раз; заслоняют и те, кто гибнет
этим же взрывом. Мягкой стороны у взрывов нет.

**Симуляция по этапам.** Рейд — последовательность этапов. На каждом
выбирается залп: точка на грани элемента, граничащего с доступной
рейдеру областью (снаряд должен долететь до неё из глаз рейдера),
взрывчатка и число единиц — одна или столько, чтобы погиб очередной
задетый элемент с учётом накопленного урона. Погибшие убираются все
сразу, доступная область пересчитывается, урон копится, и так до
пространства шкафа. Залп выбирается по одной из стратегий: ценность
открытого на серу, приближение к шкафу на серу, разрушение на серу и
«только убийства» — как рейдер, без частичного урона; везде вторым
критерием идёт число разрушаемых конструкций. Точки удара — сетка на
поверхности элемента с локальным дожиманием. Показывается самый дешёвый
по сере план среди стратегий.

## 10. Примеры

### 10.1 Закатанный шкаф (`examples/sealed-triangle-tc.json`)

Треугольный каменный фундамент, три стены по рёбрам, треугольный пол на
верху стен, шкаф в дальнем углу, двери нет. Документ целиком:

```jsonc
"defaults": { "grade": "stone" },
"elements": [
  { "id": "f1", "kind": "triangle-foundation", "position": [0, 0, 0],          "rotation": 0 },
  { "id": "w1", "kind": "wall",                "position": [0.866, 0, 0],      "rotation": 0 },
  { "id": "w2", "kind": "wall",                "position": [-0.433, 0, 0.75],  "rotation": 120 },
  { "id": "w3", "kind": "wall",                "position": [-0.433, 0, -0.75], "rotation": 240 },
  { "id": "c1", "kind": "triangle-floor",      "position": [0, 3, 0],          "rotation": 0 }
],
"deployables": [
  { "id": "tc1", "kind": "tool-cupboard", "attach": { "to": "f1", "socket": "top" },
    "offset": [-0.22, 0.382], "rotation": 300 }
]
```

Позы — те, что редактор вычисляет при установке (§4.7):

| id | position | rotation | как получено |
|---|---|---|---|
| `f1` | [0, 0, 0] | 0 | первый фундамент на пустом участке |
| `w1` | [0.866, 0, 0] | 0 | `f1.edge:0`: `a_tri · n(0°)` |
| `w2` | [−0.433, 0, 0.75] | 120 | `f1.edge:1`: `0.866 · n(120°)` |
| `w3` | [−0.433, 0, −0.75] | 240 | `f1.edge:2`: `0.866 · n(240°)` |
| `c1` | [0, 3, 0] | 0 | `top` w1 → `edge:0`, flip=false: `pos_w1 − 0.866 · n(0°)` |

Соседство: рёбра `c1` совпадают с верхами всех трёх стен, поэтому пол
опирается на все три — связей в документе для этого не нужно. Ячейка
шкафа закрыта со всех сторон и сверху.

### 10.2 Дом 2×1 с аирлоком (`examples/starter-2x1.json`)

Два квадратных фундамента: ячейка со шкафом `f1` в `[0, 0, 0]` и
тамбур-аирлок `f2` в `[3, 0, 0]`.
Внутренний проём у шкафа — `wall-frame` с двойной металлической дверью,
`opens: outward` (нормаль рамы смотрит в тамбур). Внешний одиночный
проём стоит на боковой стене тамбура в том же углу. Открытая двойная
дверь ложится поперёк прохода от наружной двери, поэтому в тамбур не
зайти, пока дверь у шкафа открыта. Сам факт перекрытия валидатор не
проверяет, это задача одной из версий 2.x (`W05`). Пример также
показывает, что на общем ребре двух фундаментов стоит проём — стена и
ячейки друг другу место не занимают (`V05`, §8), — и `offset`/`rotation`
шкафа:

```jsonc
{ "id": "d_inner", "kind": "wall-frame", "position": [1.5, 0, 0], "rotation": 0, "grade": "metal" },
{ "id": "d_outer", "kind": "doorway",    "position": [3, 0, 1.5], "rotation": 90, "grade": "metal" }
// deployables
{ "id": "door_inner", "kind": "sheet-metal-double-door",
  "attach": { "to": "d_inner", "socket": "opening" }, "opens": "outward" },
{ "id": "tc1", "kind": "tool-cupboard", "attach": { "to": "f1", "socket": "top" },
  "offset": [-1.075, -0.825], "rotation": 0 }
```

Нормаль `d_inner` (`rotation: 0`, по `+x`) смотрит в тамбур, поэтому
`outward` открывает дверь в тамбур.

### 10.3 Дом 2×2 с запрыгом (`examples/house-2x2.json`)

Классический 2×2 с входом через крышу. Первый этаж глухой: комната со
шкафом `f1` закрыта двойной дверью в `wall-frame`, за ней тамбур `f2` с
ещё одной двойной дверью, дальше `f3` с двойной дверью в ячейку
запрыга `f4`. В `f4` на полустене `hw1` лежит квадратный пол `m4`
(`position: [0, 1.5, 3]`, уровень 0.5) — он делит ячейку пополам по
высоте; сверху `hw2` (`[-1.5, 1.5, 3]`) достраивает стену до потолка.
Над `f4` пола нет: с `m4` сразу попадают в тамбур 1×1 на втором этаже,
стены которого (`u1`–`u3`, `d_roof` на `y = 3`) стоят на верхах стен
первого этажа `hw2`, `w8`, `w3`, `d_jump`; из тамбура двойная дверь
`d_roof` на крышу.
Пример показывает стопку полустен, пол на половинной высоте, уровни
0.5, 1 и 2 и виртуальное пространство тамбура без пола.

### 10.4 Шкаф в треугольнике с окном (`examples/triangle-tc-window.json`)

Треугольный фундамент, две стены и `window-frame` с укреплённым
стеклом (`strengthened-glass-window` в `opening`), шкаф в дальнем углу
фронтом к окну. Самый дешёвый рейд идёт через стекло: 140 explosive
ammo дешевле двух C4 в стену.

### 10.5 Бункер на 30 ракет (`examples/bunker-30-rockets.json`)

База, спроектированная под расчёт рейда: бронированное ядро со шкафом
без дверей, вокруг бронированная сота 3×3, над всей сотой второй этаж с
бронированными стенами и крышей, все потолки бронированные. Любой путь
к шкафу пересекает два бронированных слоя: снаружи в соту (15 ракет) и
из соты в ядро (15), сверху — крыша (15) и потолок ядра (15). Вход для
хозяина — коридор из трёх ячеек с четырьмя бронированными дверями:
4 × 5 ракет до соты плюс 15 до ядра, то есть дороже стены. Шкаф закатан:
лут передаётся через два дроп-бокса на стене ядра `cw0`, `out` и `in`. Симуляция
подтверждает: 30 ракет, 29 не хватит. Первая версия примера с комнатой
над ядром размером в одну ячейку держала только 15: угол потолка ядра
выходил на крышу соты, и залп в этот угол снимал его снаружи.

В 3D-просмотре переключатели «Материал» и «Двери» (иконками, как в
разделе строительства) всегда применяются поверх чертежа перед
проверкой схемой, по умолчанию камень и металлические двери: материал
заменяет `grade` у всех элементов, тип дверей заменяет одиночные двери на
выбранный вид, а двойные — на двойные того же вида или гаражные. Расчёт
рейда идёт уже по изменённому чертежу; бункер из §10.5 держит 30 ракет
при выборе МВК.

### 10.6 Роф-бункер (`examples/roof-bunker.json`)

Классический роф-бункер на стабильности. Комната шкафа из двух ячеек
(`f1` со шкафом и `f3`) и тамбур `f2` с дверью; на ребре между `f3` и
тамбуром каменная полустена `hw` (`[4.5, 0, 0]`). Внутри `f3` на верх
полустены положена твиговая плита `tf` на половинной высоте, а на её
ребро над полустеной поставлена каменная крыша `rb`: низкое ребро на
высоте полустены, скат поднимается над тамбуром к двери сквозь его
потолок.

```jsonc
{ "id": "tf", "kind": "square-floor", "position": [3, 1.5, 0], "rotation": 0,   "grade": "twig", "bunker": true },
{ "id": "rb", "kind": "roof",         "position": [6, 1.5, 0], "rotation": 180, "bunker": true }
```

У `rb` центр проекции над тамбуром `f2`, а `rotation: 180` разворачивает
низкое ребро `edge:0` к `x = 4.5` — на верх полустены и ребро `tf`. Над полустеной
проход закрыт крышей, под крышей — полустеной. Снаружи до твига не
добраться: он за дверью и за крышей, а изнутри хозяин ломает его одним
ударом, крыша теряет опору и падает, проход над полустеной открыт;
закрывается бункер заново плитой и крышей. В расчёте рейда стабильность
не учитывается: твиговая плита на половинной высоте в граф не входит,
ребро между тамбуром и комнатой перекрыто полустеной, крыша — наклонная
цель над тамбуром; два C4 в неё или в полустену стоят столько же,
сколько в стену, оптимально 4 300 через стену комнаты. Переключатель
«Открыть двери» роняет и плиту, и крышу.

Все шесть примеров записаны в формате 2.0 и предзагружены в разделе
«3D-просмотр» приложения; туда же можно загрузить любой документ
формата 2.0 или 1.0 (он будет переведён в 2.0). Переключатель
«Открыть двери» (или `?doors=open` в адресе) показывает все двери
распахнутыми по их `opens` и убирает крыши-затворы.

### 10.7 Хонейкомб 2×2 (`examples/honeycomb-2x2.json`)

Соло-дом по описанию «2x2 honeycombed» с rust-survival.com: ядро из четырёх
квадратных фундаментов в два этажа и хонейкомб по внешнему кольцу первого
этажа. Кольцо — восемь треугольных фундаментов на внешних рёбрах ядра и
четыре треугольника-вставки между ними, у всех треугольный потолок; стены
стоят по внешнему контуру кольца. Вход — дверной проём в треугольнике кольца
перед `f2`, затем металлическая дверь в ядро. Шкаф в углу `f1` за
металлической дверью, лут в `f3`, в `f4` — U-лестница на второй этаж к
бронированной двери. Две бойницы у входа — оконные проёмы с металлическими
решётками. Документ собран через операции редактора, поэтому все позы
сокетные.

### 10.8 Металлический форт на ящик (`examples/metal-fort.json`)

База ровно на один большой ящик металла: 48 180 фрагментов (плюс 1000 дерева
на шкаф), всё из листового металла, все двери гаражные в рамах стен. Ядро 4×4
в три этажа окружено хонейкомбом из треугольников на всю высоту. Вход —
гаражка в треугольнике кольца, отделённом стенами от соседей (шлюз на одну
клетку), затем гаражка в ядро. В центре первого этажа хранилище 2×2 со шкафом
за двумя гаражками, над ним на втором этаже внутренний хонейкомб. С третьего
этажа четыре гаражки ведут на стрелковую галерею по верхнему ярусу кольца с
решётками на каждой ровной грани. Лестницы в разных углах, выход на крышу —
будка с гаражкой, по краю крыши бруствер из полустен.

### 10.9 Дом с обороной крыши (`examples/roof-defense.json`)

Металлический дом 3×3 с хонейкомбом по первому этажу, все двери гаражные.
Вход через треугольник-шлюз в узловой зал; из зала по гаражке в каждую
комнату — к шкафу, в лут и в лестничную, без тупиковых проходов. Второй этаж
стрелковый, с амбразурами (`metal-embrasure`, горизонтальная металлическая
амбразура `shutter.metal.embrasure.a`) по центру каждой стороны. Два подъёма
на крышу в передних углах выходят в будки: гаражка наружу и оконный проём с
амбразурой, смотрящий через крышу, — высадившихся можно отстрелить, не
открывая дверь. Твёрдая сторона каждой стены (нормаль, §4.1) смотрит от более
защищённой комнаты к менее защищённой.

## 11. Как проверить документ

Схема — draft 2020-12, поэтому нужен Ajv 8 с `ajv/dist/2020`:

```bash
npm i -D ajv ajv-formats
node -e '
  const Ajv = require("ajv/dist/2020"); const addFormats = require("ajv-formats");
  const ajv = addFormats(new Ajv({ strict: true, strictRequired: false }));
  const v = ajv.compile(require("./docs/blueprint/schema/blueprint.schema.json"));
  const ok = v(require("./docs/blueprint/examples/starter-2x1.json"));
  console.log(ok || v.errors);'
```

Все шесть примеров (2.0) проходят схему, а тест
`src/blueprint/validate.test.ts` прогоняет их через `loadBlueprint` без
ошибок. Схемой отклоняются: элемент 2.0 без `position`, с `root` или с
`attach`; `bunker` у стены; дверь на `top`; `hinge` у шкафа;
`formatVersion` кроме `"1.0"` и `"2.0"`; элемент 2.0 в документе 1.0; в
документе 1.0 — элемент с `root` и `attach` одновременно и сокет
`edge:5` (проверено при обновлении спецификации). Занятость места,
высоту фундамента и соответствие дверей проёмам схема не выражает, это
валидатор (§8).

В коде загрузка — `loadBlueprint` / `parseBlueprint`
(`src/blueprint/validate.ts`): JSON → схема → для 1.0 перевод
`upgradeLegacy` → `resolveBlueprint`.

### 11.1 Режим стройки

Раздел «Строительство» всегда в режиме стройки. Слева сверху —
выпадающий список шаблонов (по умолчанию «Пустой участок»), под ним —
сведения о постройке: рейд, состав, стоимость и содержание. Грейд блоков
меняется киянкой.

Внизу сцены — панель инструментов, как слоты в игре, клавиши **1 / 2 / 3**:

- **Строительный план** — ЛКМ ставит текущий блок (новые блоки из веток),
  **зажатая ПКМ** открывает радиальное меню всех 19 конструкций: ведёшь
  мышь к пункту, отпускаешь — он становится текущим. Синий призрак встаёт
  в совместимый сокет соседнего блока. Варианты установки перебираются по
  матрице §4.5 и отсеиваются проверками движка: занятость места (`clash`,
  §8), высота фундамента, опора под низким ребром крыши. Прицел — как в
  игре (`docs/research/rust-building-mechanics.md` §2.1): луч из камеры
  пересекается с зонами выбора female-сокетов — коробками `selectSize`
  со смещением `selectCenter` в осях сокета, из префабов игры, — и
  выбирается вариант с ближайшим по лучу пересечением. Если луч ни в одну
  зону не попал, берётся вариант, ближайший к точке прицела. **R**
  перебирает варианты того же места (сторона пола или крыши, поворот
  лестницы, высота фундамента). На пустом участке первый фундамент
  встаёт в начало координат. Поставленный блок записывается в документ
  уже с позой, вычисленной `socketPose` (§4.7).
- **Киянка** — подсвечивает блок под курсором и его стабильность;
  **зажатая ПКМ** — радиальное меню: апгрейд до веток / дерева / камня /
  металла / МВК, «Повернуть» или «Снести»; **R** — снести блок под
  курсором. Снести можно любой блок, включая первый фундамент: остальные
  блоки остаются на своих местах (их позы в документе не меняются), а
  падают только те, кому не хватает стабильности (ниже 5%). Вместе с
  элементом удаляются объекты, прикреплённые к нему. «Повернуть» меняет
  `rotation`: стена разворачивается на 180° (нормалью в другую сторону),
  лестница, а также съезд и ступени, стоящие на ячейке, — на 90°, если на
  новом месте нет пересечения.
- **Объект** — ЛКМ ставит текущий объект (двери в проёмы, вставки в окна,
  шкаф, дроп-бокс), **зажатая ПКМ** — радиальное меню объектов, **R** у
  дроп-бокса меняет направление передачи.

Сдвиг камеры в орбите — средней кнопкой; в полёте прицел в центре, меню
выбирается движением мыши.

Условные модели (как в игре, см. `docs/research/rust-building-mechanics.md` §6): полная стена,
на которой ничего не стоит, стоящая на боковом ребре квадратной крыши того же уровня,
рисуется треугольником под скатом — фронтоном, вершиной к коньку. Это только вид: в
расчёте рейда стена остаётся полной.

Ещё две условные модели: **вальма** — две квадратные крыши одного грейда в
одной ячейке со скатами под прямым углом обрезают друг друга по диагонали
(угловые модели `RoofLeft/Right` с углом 90°; четыре ската над ячейкой
дают шатёр), и **угловая стойка** — где сходятся под углом торцы двух стен
одного грейда и яруса, внешний зазор заполняется столбом толщиной в стену
(`WallCornerLeft/Right`). Обе — только вид.

**Стабильность** — как в игре (`docs/research/rust-building-mechanics.md`
§4) с коэффициентами `support` из префабов: фундамент 100%; у остальных
сумма по опорным сокетам «коэффициент × стабильность опоры», не больше
100%. Стена: низ 0.7 (низкая стена 0.9) плюс по 0.1 от стен, сходящихся с
торцами; пол: по 0.25 на каждое ребро (треугольный 0.33) — верх стены или
соседний пол; крыша: 0.3 от низкого ребра; лестница: 0.7 от ячейки. На
сокете в зачёт идёт один сосед, ближайший к земле, и опора считается без
самого блока. Ниже 5% блок обрушивается: после каждого действия в режиме
стройки такие блоки сносятся каскадно, панель пишет, что упало. Призрак
показывает будущую стабильность и подсвечивается оранжевым, если блок
обрушится; киянка показывает стабильность наведённого блока. Пример: стена
на фундаменте 70–87%, пол второго этажа на четырёх стенах ≈ 87%, навес
держится на два пола, третий падает.
Камера в режиме стройки работает как обычно; в полёте прицел в центре
экрана, действия по кнопкам мыши при захваченном курсоре.

## 12. Версионирование

- `formatVersion` меняется по semver в рамках `major.minor`.
- **minor** — только добавление: новые `kind`, новые необязательные поля,
  новые коды валидации. Документ 2.0 останется валидным для 2.1.
- **major** — изменение смысла существующих полей. Требует перевода
  старых документов.
- Движок геометрии указывает свою версию в `resolved.generator`; при
  изменении констант §4.2 версия движка растёт, формат — нет.

**2.0 против 1.0.** В 1.0 элементы образовывали дерево: ровно один
фундамент с `root: true` стоял в начале координат (или в позе
`root.origin`), остальные держались `attach` за сокет родителя, а блок
без сокета-опоры — смещением `attach: {to, socket: "offset", offset,
rotation}`. Мировые позы появлялись только в `resolved`. В 2.0 поза
хранится у каждого элемента, `root` и `attach` у элементов нет, связи
следуют из геометрии. Объекты не изменились.

**Перевод 1.0 → 2.0** (`upgradeLegacy` в `src/blueprint/geometry.ts`)
выполняется при каждой загрузке документа 1.0:

1. Проверки дерева, как в 1.0: `V01`; `V02` — ровно один корень, и это
   фундамент, `attach.to` ссылается на существующий элемент, все
   элементы достижимы от корня, без циклов; `V03` — сокеты есть у типов
   (для `offset` нужно поле `offset`), для ячеек и крыш указан
   `selfSocket`; `V04` — пара сокетов разрешена матрицей §4.5, `rise`
   только у фундамента на ребре фундамента и у съезда на верху ячейки
   (0.75); `V05` — слоты сокетов §4.6 не заняты дважды; `V12` — высота
   фундамента.
2. Обход дерева от корня: каждый элемент получает позу по `socketPose`
   (§4.7).
3. Каждый элемент записывается как элемент 2.0: `id`, `kind`,
   `position`, `rotation` из обхода, `inverted` (если получился),
   `grade`, `bunker`, `label`, `notes` — из исходного элемента. `meta`,
   `defaults` и `deployables` переносятся как есть, `formatVersion`
   становится `"2.0"`.

Если на шаге 1 есть ошибки, документ не переводится и не загружается.
Переведённый документ дальше проверяется как обычный 2.0 (§8).
Обратного перевода 2.0 → 1.0 нет.

## 13. Что сознательно не вошло в 2.0

- Печи, ящики, турели, ловушки, ставни и амбразуры в `window-frame`,
  внешние стены, электрика. Для них зарезервирован массив `deployables` с новыми `kind`.
- Половинный пол и треугольная винтовая лестница — зарезервированные
  `kind`, см. §5.
- Стабильность в документе не хранится и в расчёте рейда не
  учитывается: её считает только режим стройки (§11.1).
- Террейн и перепады высот: фундамент стоит верхом на высоте 0, 1.5 или
  3 м над плоской землёй (`V12`), рельеф формат не описывает.
- Деление на здания. Корня нет, поэтому формат не запрещает держать в
  одном документе несколько несвязанных построек, но приложение не
  делит документ на здания (`buildingID` игры) и считает рейд до одного
  шкафа.
